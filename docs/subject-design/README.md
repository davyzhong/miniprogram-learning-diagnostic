阅读建议：

1. 先读数学基础文档，理解整个 MVP 的“证据链 + 学习卡点 + 验证闭环”。
2. 再读数学升级详细设计，理解为什么数学要从粗 LP 卡点升级为“知识节点 + 细卡点 + 资源重学 + 掌握状态”。
3. 再读学习卡点学习材料任务包文档，理解为什么不能只给外部链接，而要把资源转化为“学一下 + 练一下 + 复测”的小程序内任务。
4. 再读数学卡点层级升级文档，理解粗类、卡点家族、细卡点和知识节点各自承担什么系统职责。
5. 真正改数学 Prompt、报告页或数据层时，按数学诊断输出合同 v2 落字段，旧 LP 字段保留兼容。
6. 如果要把历史图片重新跑一遍，按数学历史报告全量重分析执行说明先 dry-run，再 start/finalize。
7. 再读语文设计文档，理解为什么语文要以“具体错项清单”为主，而不是只归入粗学习卡点。
8. 需要规划语文、英语的下一轮工作时，先读语文英语学习闭环升级实施设计，确认双轨边界、词汇 2.0 边界与分批交付顺序。
9. 再读英语正式文档，理解当前英语只做词汇掌握：个人词库、认词练习、纸面听写、错词本、学习记录。
10. 需要理解英语底层规则时，再读英语双功能闭环规格，重点看双维状态机、单次会话单功能、P3 补盲区联动抽词和候选词约束 OCR；但不要把发音评分、听力专项、时态句型等高阶功能提前带入当前版本。
11. 需要真正改英语代码时，再读英语技术实现文档，按数据模型、云函数 API、页面职责、迁移策略和测试计划落地，并优先完成正式文档里的 5 个当前功能。
12. 英语板块的产品与技术背景已收束为 [english/english-written-diagnosis-and-tech-decision.md](./english/english-written-diagnosis-and-tech-decision.md)。原始调研草稿保留在本地总项目知识库，不作为 GitHub 实现文档的首读入口。
13. 需要查看系统实现时，再读 `../ARCHITECTURE.md`、`../DATA_DICTIONARY.md` 和 `../CLOUD_FUNCTIONS.md`。
