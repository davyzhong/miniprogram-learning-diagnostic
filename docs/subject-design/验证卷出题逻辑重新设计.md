# 验证卷出题逻辑重新设计

> 版本：v0.1
> 日期：2026-06-18
> 状态：APPROVED（已确认设计决策，待实现）
> 定位：修复验证卷生成逻辑的 6 个根因，以细卡点（BN）为出题单位
> 前置：[验证卷自动生成设计文档](./验证卷自动生成设计文档.md)

## 一、当前问题（6 个根因）

| # | 问题 | 当前行为 | 影响 |
|---|------|----------|------|
| 1 | **粗细卡点混用** | auto-verification 优先取粗卡点 lpCode 当 target | LP-FD 下 7 个细卡点只出 3 题 |
| 2 | **题量公式太简单** | `targets.length × 3` | 3 粗卡点 = 9 题，不管细卡点数量 |
| 3 | **prompt 信息不足** | 只给 LLM 一行 `LP-FD：分数小数` | LLM 不知道具体验证什么 |
| 4 | **前后端配置不一致** | 云函数 3 题/卡点 vs 前端 5 题/卡点 | 预估 15 题实际拿 9 题 |
| 5 | **两套 LP 编码并存** | LP-FD（助记）vs LP-001（数字） | 混用不报错但映射断裂 |
| 6 | **taxonomy 元数据未利用** | microValidationRules/symptomPatterns 没进 prompt | LLM 出题质量低 |

## 二、已确认的设计决策

| 决策 | 选择 |
|------|------|
| 出题粒度 | **每个 BN 细卡点 2 题**（1 核心 + 1 延展） |
| 总题量上限 | **15-20 题**（约 2-3 张 A4 纸） |
| 覆盖策略 | 粗卡点展开为细卡点，按 severity 优先级截取 |

## 三、重新设计后的出题流程

```
pendingBottlenecks（粗卡点）
  ↓ 展开
BN 细卡点列表（去重，附 severity）
  ↓ 按 severity 排序，截取上限
selectedBottlenecks = sort(prioritized).slice(0, MAX_BN_COUNT)
  ↓ 题量计算
expectedCount = selectedBottlenecks.length × 2
  ↓ 构建 prompt（含微验证规则）
LLM 生成 → 截断到 expectedCount
```

### 3.1 粗卡点 → 细卡点展开

```
LP-FD（分数小数，severity=high）
  → BN-FRACTION-ADD-DENOM-MISMATCH（通分方向错误）
  → BN-DEC-MUL-POINT-COUNT（小数点定位错误）
  → BN-FRACTION-DIV-RECIPROCAL-MISSING（分数除法倒数缺失）
  → BN-FRACTION-MUL-SIMPLIFY-DIRECTION（化简方向错误）
  → BN-FRACTION-DECIMAL-MIXED-LOAD（分数小数互化负荷）
  → BN-AXIS-FOLD-MIDPOINT-DIRECTION（数轴折叠方向）
  → BN-CIRCLE-AREA-EXTRA-R（圆面积增量计算）
```

7 个细卡点 × 2 题 = 14 题。如果只有 1-2 个粗卡点，题量 14-20 题，合理。

### 3.2 题量计算公式

```js
// 每个 BN 细卡点出 2 题（1 核心 + 1 延展）
const QUESTIONS_PER_FINE_BOTTLENECK = 2;
const CORE_QUESTIONS_PER_BN = 1;
const EXTENSION_QUESTIONS_PER_BN = 1;

// 总题量上限
const MAX_TOTAL_QUESTIONS = 20;
const MIN_TOTAL_QUESTIONS = 6;

// 从所有细卡点中按 severity 优先级截取
const MAX_FINE_BOTTLENECKS = Math.floor(MAX_TOTAL_QUESTIONS / QUESTIONS_PER_FINE_BOTTLENECK); // = 10

function calculateExpectedCount(fineBottlenecks) {
  const count = Math.min(fineBottlenecks.length, MAX_FINE_BOTTLENECKS);
  const expectedCount = count * QUESTIONS_PER_FINE_BOTTLENECK;
  return Math.max(MIN_TOTAL_QUESTIONS, Math.min(MAX_TOTAL_QUESTIONS, expectedCount));
}
```

### 3.3 prompt 增强：填充 taxonomy 微验证规则

改前（一行笼统描述）：
```
验证卡点：LP-FD：分数小数；LP-RP：比例比值
```

改后（每个 BN 附带微验证规则）：
```
验证以下学习卡点，每个出 2 题（1 核心验证 + 1 迁移延展）：

1. BN-FRACTION-ADD-DENOM-MISMATCH（通分方向错误）
   典型症状：分数加减时分母直接相加
   验证方向：给异分母分数加减题，检查是否先通分

2. BN-DEC-MUL-POINT-COUNT（小数点定位错误）
   典型症状：小数乘法积的小数点位置错误
   验证方向：给小数乘法题，检查积的小数位数
...
```

这些信息从 `bottleneck-taxonomy-v2.seed.json` 的 `symptomPatterns` / `microValidationRules` 字段提取。

## 五、粗卡点 → 细卡点展开的数据来源

`pendingBottlenecks` 每条已有 `candidateBottlenecks` 字段（来自 `learningMapProfileFields`）：

```js
// pendingBottleneck 结构
{
  lpCode: 'LP-FD',           // 粗卡点
  lpName: '分数小数',
  severity: 'high',
  candidateBottlenecks: [     // ← 细卡点列表
    { bottleneckId: 'BN-FRACTION-ADD-DENOM-MISMATCH', title: '通分方向错误', evidenceStrength: 'high' },
    { bottleneckId: 'BN-DEC-MUL-POINT-COUNT', title: '小数点定位错误', evidenceStrength: 'medium' },
    ...
  ]
}
```

展开逻辑：
1. 遍历 pendingBottlenecks
2. 对每条，遍历 candidateBottlenecks，提取 `bottleneckId` + `title` + `evidenceStrength`
3. 如果某条 pendingBottleneck 没有 candidateBottlenecks（只有粗卡点），用粗卡点 lpCode 作为 fallback target（但标注 `coarse: true`，prompt 里给出更详细的描述）
4. 去重、按 severity/evidenceStrength 排序
5. 截取最多 MAX_FINE_BOTTLENECKS（10）个

## 六、prompt 结构设计

```
你是数学老师，生成验证试卷。

学生：钟青羽，6年级
本次验证覆盖 N 个细分学习卡点（来自 M 个大类），共出 X 题：

1. [高] BN-FRACTION-ADD-DENOM-MISMATCH（通分方向错误）
   症状：分数加减时分母直接相加（如 1/2+1/3=2/5）
   验证：异分母加减，检查通分步骤

2. [高] BN-DEC-MUL-POINT-COUNT（小数点定位错误）
   症状：小数乘法积的小数位数错误
   验证：小数乘法，检查积的小数点位置

...

要求：
1. 每个卡点出 2 题：1 道核心验证题 + 1 道迁移延展题
2. 核心题直接复现该卡点的典型错误场景
3. 延展题变换情境（不同数字/不同表述），观察是否稳定
4. 难度匹配 6 年级
5. lpCode 填对应的 BN 细卡点 ID，lpName 填卡点中文名
6. 直接返回 JSON

输出格式：
{"title":"...","questions":[{"index":1,"content":"...","answer":"...","points":5,"lpCode":"BN-...","lpName":"..."}]}
```

## 七、风险与缓解

| 风险 | 缓解 |
|------|------|
| LLM 生成 20 题可能超时 | prompt 精简，每 BN 只给 2 行（症状+验证），不塞全文 |
| candidateBottlenecks 为空时退化为粗卡点 | fallback 逻辑：粗卡点出 2 题，prompt 给更详细描述 |
| 前端题量预估又要改 | 统一常量到一处（cloud.js 或 constants.js），前后端共用 |
