# 验证卷自动生成设计文档

> 版本：v0.1
> 日期：2026-06-17
> 状态：DRAFT（待实现）
> 定位：把验证卷从"用户手动点击生成"改为"诊断报告完成后后台自动生成"，用户只需预览、打印、上传作答。

## 一、背景与动机

### 当前流程的痛点

```
当前：上传→诊断报告→用户手动进卡点页→点"生成验证卷"→等LLM(60s)→预览→打印
```

1. **用户要主动触发**：报告页、学科工作台、卡点中心、卡点详情、首页共有 6 个入口都导向"手动生成验证卷"，用户需要理解"什么是验证卷"并主动点击。
2. **等待体验差**：LLM 生成试卷需要 30-60 秒，用户点击后必须等待，期间页面 loading。
3. **入口分散**：6 个入口（报告页×2、学科工作台、卡点中心、卡点详情、首页/档案页）的逻辑各自独立，维护成本高。

### 目标流程

```
改后：上传→诊断报告→（后台自动生成验证卷）→用户直接预览→打印→上传作答
```

1. **零等待**：用户看完报告想打印验证卷时，它已经生成好了。
2. **零理解成本**：用户不需要理解"生成验证卷"这个动作，只需"预览→打印"。
3. **解决超时**：异步生成不受前端 60 秒超时限制。

## 二、已确认的设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| **触发条件** | 有 `pendingBottlenecks` 就自动生成 | 没卡点就不浪费 LLM 调用 |
| **覆盖策略** | 新诊断覆盖旧卷（旧的标记 `superseded`） | 始终用最新诊断结果 |
| **失败处理** | 自动重试 N 次（3次，间隔递增） | 提高可靠性 |
| **状态获取** | 每页独立调 `getActiveVerificationPaper` | 简单直接，状态实时 |

## 三、自动生成引擎设计

### 3.1 触发时机

诊断报告分析完成后，在 `analyzePhotos/index.js` 的 `writeCompletedAnalysis` 函数结尾挂载：

```js
// analyzePhotos/index.js — writeCompletedAnalysis 结尾（行 631 后）
if (profileSummary.isEffective && (profile.pendingBottlenecks || []).length > 0) {
  triggerAutoVerificationPaper(reportId, studentId, subject, profile)
    .catch(err => console.warn('auto verification paper failed:', err.message))
}
```

触发条件：`profileSummary.isEffective`（报告有效）且 `pendingBottlenecks.length > 0`（有待验证卡点）。

### 3.2 覆盖策略

触发自动生成前，先把该学科已有的"未验证验证卷"标记为 `superseded`：

```js
async function triggerAutoVerificationPaper(reportId, studentId, subject, profile) {
  // 1. 覆盖旧卷：标记同学科未验证的旧验证卷为 superseded
  const oldPapers = await db.collection('papers')
    .where({ studentId, subject, type: 'verification', generationStatus: db.command.neq('superseded') })
    .get()
  for (const old of oldPapers.data) {
    // 如果旧卷还没验证过（没有对应的验证报告），才覆盖
    const hasVerification = await hasVerificationReport(studentId, subject, old._id)
    if (!hasVerification) {
      await db.collection('papers').doc(old._id).update({
        data: { generationStatus: 'superseded', supersededAt: new Date(), supersededBy: reportId }
      })
    }
  }

  // 2. 创建新验证卷记录（状态 generating）
  const targets = extractTargets(profile)  // 从 pendingBottlenecks 提取卡点列表
  const paperId = await createPaperRecord({
    studentId, subject, type: 'verification', targets,
    generationStatus: 'generating', autoGenerated: true,
    triggeredByReport: reportId
  })

  // 3. 调生成逻辑（带重试）
  await generateWithRetry(paperId, studentId, subject, targets, 0)
}
```

### 3.3 失败重试机制

```js
async function generateWithRetry(paperId, studentId, subject, targets, attempt) {
  const MAX_ATTEMPTS = 3
  const RETRY_DELAYS = [0, 10000, 20000]  // 首次立即、10s后、20s后

  try {
    // 调用 generatePaper 的核心逻辑（提取为可复用函数）
    const result = await generateVerificationPaperCore(studentId, subject, targets)
    await db.collection('papers').doc(paperId).update({
      data: { generationStatus: 'ready', generationAttempts: attempt + 1, ...result }
    })
  } catch (err) {
    if (attempt + 1 < MAX_ATTEMPTS) {
      // 记录失败，等待后重试
      await db.collection('papers').doc(paperId).update({
        data: { generationAttempts: attempt + 1, generationError: err.message }
      })
      await new Promise(r => setTimeout(r, RETRY_DELAYS[attempt + 1]))
      return generateWithRetry(paperId, studentId, subject, targets, attempt + 1)
    } else {
      // 最终失败
      await db.collection('papers').doc(paperId).update({
        data: { generationStatus: 'failed', generationAttempts: attempt + 1, generationError: err.message }
      })
    }
  }
}
```

### 3.4 云函数超时处理

`analyzePhotos` 本身可能已经运行了较长时间，剩余时间不够调 `generatePaper`（LLM 需要 30-60 秒）。

两种策略（实现时选其一）：
- **策略 A（优先）**：如果 `analyzePhotos` 剩余时间充足（>60s），直接在函数内调生成。通过 `cloud.callFunction({ name: 'generatePaper', data: {...} })` 调子函数，避免代码重复。
- **策略 B（兜底）**：如果剩余时间不足，只创建 `generationStatus: 'generating'` 的 paper 记录，依赖下次 `getAnalysisProgress` 轮询时触发补生成。

推荐策略 A——`analyzePhotos` 配置了 60 秒超时，分析本身通常在 20-30 秒完成，剩余时间足够调 `generatePaper`。如果不够，降级到策略 B。

## 四、数据模型变更

### 4.1 `papers` 表新增字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `autoGenerated` | boolean | 是否自动生成（true）vs 用户手动生成（false） |
| `generationStatus` | string | 生成状态：`generating` / `ready` / `failed` / `superseded` |
| `generationAttempts` | number | 重试次数（0=首次尝试，1/2=重试） |
| `generationError` | string | 失败原因（成功时为空） |
| `triggeredByReport` | string | 触发自动生成的诊断报告 ID |
| `supersededAt` | date | 被覆盖的时间 |
| `supersededBy` | string | 覆盖它的新诊断报告 ID |

### 4.2 状态机

```
generating ──成功──→ ready
    │                   │
    │失败重试            │用户上传作答
    ↓                   ↓
  failed            (验证报告生成后，该卷"完成使命")
    │
    │用户手动重试
    ↓
  generating（重新进入循环）
```

`superseded` 是终态——被新诊断报告覆盖的旧卷，不再激活。

### 4.3 "当前激活的验证卷"定义

一个学生 + 一个学科，同时只有一份 `generationStatus: 'ready'` 的验证卷是"激活的"。查询逻辑：

```js
// studentData 云函数新增 action
async function getActiveVerificationPaper(studentId, subject) {
  const res = await db.collection('papers')
    .where({ studentId, subject, type: 'verification' })
    .orderBy('createdAt', 'desc')
    .limit(5)
    .get()

  // 优先找 ready 状态的
  const ready = res.data.find(p => p.generationStatus === 'ready')
  if (ready) return { paper: ready, status: 'ready' }

  // 其次找 generating
  const generating = res.data.find(p => p.generationStatus === 'generating')
  if (generating) return { paper: generating, status: 'generating' }

  // 其次找 failed
  const failed = res.data.find(p => p.generationStatus === 'failed')
  if (failed) return { paper: failed, status: 'failed' }

  // 没有任何自动生成的卷
  return { paper: null, status: 'none' }
}
```

## 五、前端入口改造方案

### 5.1 改造原则

**所有"生成验证卷"入口，改为"状态分流"**：

```
入口点击 → 调 getActiveVerificationPaper(studentId, subject)
  → status === 'ready'    → 跳 paper-preview（直接预览/打印）
  → status === 'generating' → 提示"验证卷生成中…"（禁用或跳预览页显示进度）
  → status === 'failed'     → 跳 generate-verification（手动重试）
  → status === 'none'       → 跳 generate-verification（兜底手动生成）
```

### 5.2 逐页面改造清单

#### 报告页 `report`（2 个入口）

| 原按钮 | 改后（status=ready） | 改后（status=generating） | 改后（status=failed） | 改后（status=none） |
|--------|---------------------|--------------------------|----------------------|---------------------|
| 底部"＋生成纸面验证卷" | "查看验证卷"→跳预览 | "验证卷生成中…"→禁用 | "点击重试"→跳生成页 | "生成验证卷"→跳生成页 |
| 结论卡"生成纸面验证卷" | 同上 | 同上 | 同上 | 同上 |

改动文件：

- `report.js`：`onGenerateVerification` 改为状态分流跳转

#### 学科工作台 `subject-home`（1 个入口）

主任务卡按钮文案随 paper 状态变化：
- ready → **"验证卷已就绪，去打印"**
- generating → **"验证卷生成中…"**
- failed → **"验证卷生成失败，重试"**
- none → 保持原来的 **"生成纸面验证卷"**

改动文件：

#### 卡点中心 `bottleneck-center`（1 个入口）

每个卡点卡片的"验证"按钮：
- 该学科已有 ready 验证卷 → 按钮变成 **"查看验证卷"**，跳 paper-preview
- 否则保持"验证"，跳 generate-verification

改动文件：`bottleneck-center.js`：`onGenerateForBottleneck` 加状态判断

#### 卡点详情 `bottleneck-detail`（1 个入口）

底部"生成纸面验证卷"按钮：逻辑同学科工作台。
关联验证卷展示（`onViewPaper`）**不用改**——它本来就是展示已生成的卷。

改动文件：`bottleneck-detail.js`：`onGenerateVerification` 加状态判断

#### 首页 / 档案页（2 个入口 via shared-navigation）

`shared-navigation.js` 的 `onBottleneckAction` 和 `onPrimaryAction`：
- 原来 `primaryText === '生成纸面验证卷'` 时跳 generate-verification
- 改为：先查 paper 状态，ready 跳 paper-preview，否则跳 generate-verification

改动文件：
- `shared-navigation.js`：两个函数加状态分流

## 六、generate-verification 页面的角色变化

这个页面**不删除**，但从"主流程页面"降级为"兜底/重试页面"：

| 场景 | 用户如何进入 | 页面行为 |
|------|-------------|----------|
| 自动生成失败 | 入口 status=failed → 跳生成页 | 显示"自动生成失败，请手动选择卡点重新生成" |
| 用户想手动选卡点 | 入口 status=none → 跳生成页 | 正常流程（选卡点→生成） |
| 用户想覆盖已有卷 | 主动从某处进入 | 显示"系统已自动生成验证卷（X月X日），你可以重新选择卡点生成新的" |

## 八、风险与注意事项

| 风险 | 影响 | 缓解 |
|------|------|------|
| LLM 生成时间不可控（可能 >60s） | 云函数超时 | 重试机制 + 策略 B 兜底（标记 generating，下次轮询补生成） |
| 用户连续上传多份诊断报告 | 触发多次自动生成 | 覆盖策略：新卷标记旧卷 superseded，始终只激活一份 |
| 自动生成消耗 LLM 配额 | 成本增加 | 只在有 pendingBottlenecks 时触发；失败重试有上限（3 次） |
| 前端入口改造范围大 | 回归风险 | 分阶段实现，先改报告页和学科工作台（最高频入口），再改其他 |
