## 一、验证卷在产品闭环中的定位

```
拍照诊断 → 诊断报告（全量卡点快照） → 验证卷（纸面复测） → 批改反馈 → 更新卡点置信度
                ↑                                                    |
                └──────────────── 下次诊断反映改善情况 ←────────────┘
```

**核心原则**（用户明确要求）：
> 诊断报告跟验证卷是对应匹配的。要根据每一次对当下全量的学科情况进行诊断，给出全量的信息。同时根据这份诊断报告，产生验证卷。最后通过完成验证卷，来反馈本次诊断后，进行"反馈学习"的成果如何。

- 验证卷是诊断报告的**纸面延伸**——把报告里的卡点转化为可手写作答的题目
- 每一份诊断报告**对应一份验证卷**（`report.verificationPaperId` ↔ `paper.triggeredByReport`）
- 验证卷是**异步自动生成**的，用户无需点击"生成"

## 二、内容要求

### 2.1 全量卡点覆盖（CRITICAL）

| 要求 | 说明 |
|------|------|
| **全量细卡点** | 验证卷必须覆盖诊断报告对应 profile 里的**全部待验证细卡点（BN）**，不能只覆盖部分 |
| 数据来源 | `profile.pendingBottlenecks` + `profile.currentBottlenecks`，展开 `candidateBottlenecks` 得到全量 BN |
| 展开逻辑 | `extractFineBottlenecks(profile)`：读两个字段，合并去重，按 weight 降序排列 |
| 不截断 | 不再有 `MAX_SELECTED_BOTTLENECKS = 10` 之类的硬上限 |

### 2.2 置信度驱动分层出题

每个 BN 的出题数由其 **weight（置信度权重）** 决定：

| 置信度层级 | weight 范围 | 出题数 | 题目构成 |
|-----------|------------|--------|---------|
| 高置信 | ≥ 75 | **3 题** | 2 道核心题（复现典型错误，不同数字）+ 1 道迁移题（变换情境） |
| 中置信 | 45-74 | **2 题** | 1 道核心题 + 1 道迁移题 |
| 低置信 | < 45 | **1 题** | 1 道核心题 |

**阈值常量**（前后端必须一致）：
- `CONFIDENCE_HIGH_THRESHOLD = 75`
- `CONFIDENCE_MEDIUM_THRESHOLD = 45`

**总题量公式**：`Σ questionsForWeight(weight)` = 高置信BN数×3 + 中置信BN数×2 + 低置信BN数×1

### 2.3 题目质量要求

| 要求 | 说明 |
|------|------|
| **核心题** | 直接复现该卡点的典型错误场景，换不同数字 |
| **迁移题** | 变换情境（不同表述/不同数字），观察是否稳定掌握 |
| **难度** | 匹配学生年级 |
| **explanation（解题过程）** | 每题必须包含**本题专属的**具体解题步骤：具体数字的计算过程 + 关键判断点。**严禁**模板化废话（如"分析题目条件""确定运算顺序""注意检查"） |
| **无 LaTeX** | 题目和答案中**禁止使用 LaTeX 公式**（如 `\frac`）。分数写成 `3/4` 格式，乘号用 `×`，除号用 `÷` |
| **去重** | 每道题的 explanation 必须不同，紧扣该题的具体数字和考点 |

### 2.4 答案页要求

| 要求 | 说明 |
|------|------|
| 每题答案 | 必须有答案 |
| **解题过程** | 必须展示 explanation（解题步骤），不能只有答案 |
| 格式 | 卡点名 + 答案 + 解题思路（explanation） |

## 三、生成流程

### 3.1 触发时机

| 场景 | 触发方式 |
|------|---------|
| **诊断报告完成后** | `analyzePhotos` 云函数自动触发 `triggerAutoVerificationPaper`，创建验证卷记录并调度后端短任务续跑 |
| **用户点击"查看/下载验证卷"** | 统一入口 `navigateToVerificationPaper` 只检测状态：ready 进入下载页，generating/appending 轮询等待 |
| **生成失败/未生成** | 前端只提示状态，不创建新卷、不驱动出题；需要通过重新诊断或后端维护任务修复 |

### 3.2 异步自动生成（v4 短任务续跑）

**重要约束**：真实数学样本里，30+ 细卡点验证卷不能在一次云函数调用内稳定生成。即使分成 2-8 个 BN/批，也可能触发 60 秒调用超时。

**正确做法**：
1. **`analyzePhotos`**：诊断完成后自动触发 `triggerAutoVerificationPaper`。
2. **`triggerAutoVerificationPaper`**：只创建 `generationStatus: 'generating'` 的 paper 记录，写入 `generationProgress`，回写 `report.verificationPaperId / verificationPaperStatus`。
3. **短任务续跑**：调用 `regenerateVerificationPaper?action=continue`，每次只推进 1 个未生成 BN；成功后由后端继续调度下一次。
4. **最终合成**：最后一个 BN 生成完成后，`continue` 调用 `generatePaper(_regeneratePdf)` 统一重排学生页和答案页，写入 PDF 并标记 `ready`。
5. **前端统一入口**：只调用 `getActiveVerificationPaper` 查状态。ready 进入 `paper-preview` 下载；generating/appending 显示"后台生成中"并轮询；failed 或卡死（stale）弹窗引导家长自助恢复（见 3.2.1）；none 只提示状态。
6. **禁止前端直接出题**：`navigateToVerificationPaper` 不得调用 `generatePaper(_appendToPaperId)` 拼批次。

#### 3.2.1 卡死检测与家长自助恢复（2026-07-17 新增）

续跑链每一步都是 fire-and-forget 调度，任一 `continue` 调度启动失败（非生成失败）会让 paper 永久停在 `generating/appending`。为此增加恢复路径：

1. **stale 检测**：续跑链每一步都会写 `papers.updatedAt`。`studentData?action=getActiveVerificationPaper` 对 generating/appending 且 `updatedAt`（或 `generatedAt`/`createdAt`）距今超过 10 分钟的卷返回 `stale: true`。
2. **resume action**：`regenerateVerificationPaper?action=resume` 是家长自助恢复入口——`requireStudentAccess` 校验权限；generating/appending 但 10 分钟内有写入的卷拒绝恢复（防止与活跃续跑链并发双链）；failed 卷先重置为 generating 再接入 `continueGeneration`（幂等：跳过已生成目标、继续下一个、全部完成后合成 PDF）。
3. **前端引导**：`navigateToVerificationPaper` 在 `stale === true` 或 `failed` 时弹窗（"验证卷生成时间较长，可能已中断，是否继续生成？" / "验证卷生成失败，是否重试？"），确认后调用 `resume`（前端 60s 超时）并恢复轮询，ready 后自动进入 `paper-preview`。

### 3.3 分批生成（规避 60 秒超时）

| 配置 | 值 | 说明 |
|------|-----|------|
| `BATCH_SIZE` | 1 个 BN/批 | 单次只调一个目标，最大化规避 60s 调用超时 |
| 重试 | 3 次/批 | 单批失败独立重试 |
| 追加模式 | `_appendToPaperId` | 题目追加到 paper.questions，不重新生成 PDF |
| 最终 PDF | `_regeneratePdf` | 全部批次完成后，重新分页 + 生成 PDF |

**后端短任务流程**（`triggerAutoVerificationPaper` → `regenerateVerificationPaper?action=continue`）：
```
1. analyzePhotos 完成诊断报告
2. triggerAutoVerificationPaper 创建 paper，并写入 triggeredByReport / generationProgress
3. continue 读取 paper.questions，跳过已生成目标，只推进下一个未生成 BN
4. 当前 BN 成功后更新 generationProgress，并继续调度下一次 continue
5. 全部目标成功后调用 generatePaper(_regeneratePdf) 生成最终 PDF
6. 成功：paper.generationStatus = ready，report.verificationPaperStatus = ready
7. 失败：paper.generationStatus = failed，report.verificationPaperStatus = failed
```

### 3.4 expectedCount 计算

```
// 云函数 generatePaper 内部
expectedCount = Σ questionsForWeight(weight)
// 不是 targets.length × 2（旧逻辑，已废弃）
```

与 prompt 里的置信度标签 `[高置信·出3题]` 完全一致，`normalizeQuestionsData` 的数量校验阈值同步对齐。

## 四、PDF 格式规范

### 4.1 页面规格

| 配置 | 值 |
|------|-----|
| 纸张 | A4（595×842pt） |
| 页边距 | 上 56pt，下 50pt，左右 40pt |
| 字体 | NotoSansCJKsc-Regular（思源黑体） |
| 正文字号 | 10pt |
| 双栏 | 左右两栏，栏宽 ~240pt，栏间距 20pt |

### 4.2 分页与排序规则

| 规则 | 说明 |
|------|------|
| **按题数均匀分页** | `_regeneratePdf` 时按实际题目数量分页，每页 **10 题**（双栏 5 行），不按原始 targets 分页 |
| 分页公式 | `totalPages = ceil(questionCount / 10)` |
| pageCode 格式 | `MATH-V-{dateCode}-{sequence}-P{pageIndex}` |
| 换页阈值 | 当前行（含卡点标签）放不下当前页剩余空间时换页 |
| **不留大空白** | 底部留白不超过一题高度（~60pt）；放得下就放，放不下才换页，题目回退到下一页 |
| **同卡点排序**（CRITICAL） | 分页前先按 lpCode 分组排序（stable sort），让同卡点的题目**连续排列**。这样双栏配对时左右栏尽量是同一卡点，避免不同卡点交错 |
| **统一编号**（CRITICAL） | 排序后重新分配 `index`（1, 2, 3... 连续），覆盖 LLM 批次内的重复编号（每批从 1 开始） |

### 4.3 学生页布局

| 元素 | 规格 |
|------|------|
| **页头** | 学生名 + 学科 + 日期 + 卷号 + 页码 + pageCode |
| **卡点标签（栏内跟随）** | **不占整行**，只占所在栏的宽度（栏宽 × 65%）。左栏的卡点标签在左栏题目上方，右栏的在右栏题目上方。左右栏各自独立跟踪 lpCode 变化，各自画标签 |
| 标签格式 | `卡点名称  验证N题·置信度`（左侧卡点名 9pt 蓝色，右侧标注 7.5pt 灰色），下方浅色下划线 |
| **卡点跟随题目** | 标签只在该卡点的第一道题之前出现（栏内）。同一卡点的多道题连续排列不重复画。换页后重置（新页第一题重画标签） |
| **题目双栏** | 左右两栏**严格对齐**：文字区统一高度（取左右较大者）、演算区统一高度（52pt）、演算区从同一 Y 坐标开始 |
| **题目编号** | 全局连续编号（1, 2, 3...），左上角带编号 + 演算虚线框（统一 52pt 高） |
| **跨 group 配对** | 同 pageCode 下所有题目连续双栏配对。同卡点排序后，大部分行左右栏是同一卡点；奇数题卡点的最后一题会和下一个卡点的首题配对 |

### 4.4 答案页布局

| 元素 | 规格 |
|------|-----|
| 页头 | 标注"答案与解析" + 卷号 + 页码 |
| 每题 | 卡点名 + 答案 + **解题过程（explanation）** |
| 双栏 | 同样双栏排列 |

### 4.5 渲染约束

| 约束 | 说明 |
|------|------|
| **LaTeX 清理** | `cleanLatex()` 在 `cleanPromptText` 内调用，把 `\frac{a}{b}` → `a/b`（简单数字不加括号），`\times` → `×`，`\div` → `÷`，`\sqrt` → `√` 等 |
| **卡点名不截断** | 标签用 `heightOfString` 计算实际高度，支持自动换行，不截断加 `…` |
| **卡点标签栏内跟随** | 标签只占栏宽（非全宽），不独占整行。左右栏各自独立（`drawColumnGroupLabel`） |
| **卡点名无字母编号** | 不加 A/B/C/D 前缀，直接显示卡点名称 |
| **题目统一编号** | 排序后 `index = idx + 1` 连续编号，不用 LLM 批次内编号 |
| **演算区对齐** | 左右栏演算区高度统一（52pt），文字区取 `max(左右 contentHeight)` 对齐，演算区从同一 Y 开始 |
| **紧凑布局** | 标签高度 = 文字高度 + 5pt（含下划线）；题目行高 = 对齐文字高度 + 52 + 4 + 10 |

## 五、统一入口与状态管理

### 5.1 统一入口函数

所有页面的"查看验证卷"按钮**统一调用** `navigateToVerificationPaper`（`shared-navigation.js`）：

| 验证卷状态 | 行为 |
|-----------|------|
| `ready` | 直接跳 `paper-preview` |
| `generating` / `appending` | Toast + 轮询（5s/次，最多 24 次=2分钟），ready 后自动跳 |
| `failed` | 提示后台生成失败，不在前端创建新卷 |
| `none` | 提示暂无验证卷，请先完成诊断 |

### 5.2 入口清单（全部统一）

| 页面 | 按钮文案 | 调用 |
|------|---------|------|
| 诊断报告页 | "查看验证卷" | `navigateToVerificationPaper(cloud, {studentId, subject, reportId})` |
| 卡点详情页 | "查看验证卷" | 同上（reportId 为空） |
| 学科首页 | "查看/下载验证卷" | 同上 |
| 卡点中心页 | 卡点行操作 | 同上 |
| 学生档案页 | "下载验证卷" 主动作 | 同上 |
| 首页 | "查看/下载验证卷" 或 "进入试卷" | 同上或直接进入 `paper-preview` |

### 5.3 下载与上传动作契约（不可省略）

验证卷 ready 以后，前台可见的核心动作必须遵守以下四条：

1. **主动作永远是下载验证卷**：`paper-preview` 的主按钮为"下载验证卷"，不能因为已经下载过而切换成"上传"或"查看反馈"。
2. **允许重复下载**：下载状态只用于提示进度，不用于禁止再次下载；用户找不到文件时可以反复打开 PDF。
3. **上传作答是独立二级动作**：纸面作答完成后，通过独立的"上传作答照片"入口进入 `upload?mode=verification&paperId=...`。
4. **反馈报告不替代下载**：验证反馈完成后，仍保留"下载验证卷"主动作，"查看验证反馈"作为二级动作或反馈卡入口。

### 5.4 paper 状态流转

```
generating → appending（每批追加时更新 generationProgress）→ ready
                ↓
              failed（全部批次失败）
```

### 5.5 轮询配置

| 配置 | 值 |
|------|-----|
| 轮询间隔 | 5000ms |
| 最大次数 | 24 次（2 分钟） |
| 超时提示 | "生成时间较长，请稍后从学科首页查看" |

## 六、数据模型

### 6.1 papers 集合关键字段

| report 字段 | 说明 |
|-------------|------|
| `verificationPaperId` | 关联的 paper ID |
| `verificationPaperStatus` | `generating` / `ready` / `failed` |

### 6.3 question 对象结构

```js
{
  index: 1,                  // 全局连续编号（排序后重新分配，非 LLM 批次内编号）

  questionId: "MATH-V-20260620-01-P01-Q01",
  targetType: "fine_bottleneck",
  points: 10
}
```

## 七、限制条件与已知约束

### 7.1 技术限制

| 限制 | 说明 | 应对 |
|------|------|------|
| **云函数 60s 超时** | 单次 generatePaper 调用必须在 60s 内完成 | 短任务续跑：每次只追加 1 个 BN，最后统一重排 PDF |
| **进程销毁** | 云函数 return 后异步任务被终止 | `analyzePhotos` 只创建记录并调度 `regenerateVerificationPaper?action=continue`，由独立云函数链式推进；前端不驱动出题 |
| **LLM 合并 BN** | LLM 可能把语义重叠的 BN 合并到同一 lpCode（如 3 个面积换算 BN → 1 个 lpCode 出题） | 可接受，覆盖了主要考点 |
| **taxonomy 缺失** | 部分 AI 生成的变体 BN 编码不在 taxonomy seed 里 | `buildTargetDescWithRules` 降级时附上父级名称给 LLM 上下文 |

### 7.2 内容限制

| 限制 | 说明 |
|------|------|
| **禁止 LaTeX** | 题目/答案/explanation 中不能出现 `\frac`、`\times` 等 LaTeX 命令 |
| **禁止模板废话** | explanation 不能是"分析题目条件"等通用表述 |
| **禁止截断卡点名** | group bar 必须完整展示卡点名称（自动换行） |
| **禁止固定题数** | 不能再用"每卡点固定 2 题"的旧逻辑 |

## 八、一致性原则（与全局规范对齐）

### 8.1 计数口径

验证卷的卡点数必须与诊断报告、学科首页、知识地图等页面的计数口径一致：

- **待验证 = `status !== 'improved'`**（含 needs_verification + persisting + recurring）
- **数学展开细卡点**：所有计数都基于展开后的 BN（不是粗卡点 LP）
- 详见 `CLAUDE.md` 的"全局信息一致性原则"

### 8.2 置信度展示

验证卷的 group bar 标注置信度标签（高/中/低），与学习地图、诊断报告、卡点详情页的置信度展示一致。
