# 置信度驱动分层验证模型设计文档

> 版本：1.0 | 更新：2026-06-19 | 状态：已实现
>
> 本文档定义了学习卡点的置信度模型、分层验证策略、以及全链路展示规范。
> 所有涉及卡点出题、卡点统计、置信度展示的代码都必须遵循本文档。

## 1. 设计背景

### 1.1 问题
旧模型中，每个卡点（BN）统一出 2 题，所有卡点的验证强度完全相同。
这导致：
- 反复出现、多次验证未通过的高置信卡点，验证力度不够
- 初次发现、证据薄弱的低置信卡点，浪费了不必要的出题量
- 卡点的 weight（0-100 权重）已经动态计算了置信度信息，但出题时完全没利用

### 1.2 目标
- **差异化验证**：高置信卡点重点验证（3题），中置信正常验证（2题），低置信轻量观察（1题）
- **置信度外显**：在所有用户可见的卡点触点（学习地图、诊断报告、验证卷、卡点详情）统一展示置信度
- **全链路一致**：同一份卡点数据在不同页面展示的统计口径完全一致

## 2. 置信度模型

### 2.1 weight 计算（已有，`profile-summary.js`）

| 事件 | weight 变化 | 说明 |
|---|---|---|
| 新卡点首次出现 | 50 + min(30, errorCount × 5) | 基线 50，每个相关错题 +5 |
| 再次出现（persisting） | +20 | 证据增强 |
| 曾改善后复发（recurring） | +30 | 重点关注 |
| 验证未通过 | +15 | 需要继续练习 |
| 验证通过第 1 次 | -30 | 初步改善 |
| 验证通过第 2 次及以上 | -40 | 稳定改善 |

weight 范围：0-100（`clampWeight` 钳制）。界面统一称为“综合置信分”，分数越高表示证据更充分、越需要优先处理。它不是模型准确率，也不是孩子答题正确率。

### 2.2 置信度分层（新增）

| 档位 | weight 范围 | 含义 | 验证题数 | 题目结构 |
|---|---|---|---|---|
| **高置信** | ≥75 | 反复出现、多次验证未通过，确凿卡点 | **3 题** | 2 核心 + 1 迁移 |
| **中置信** | 45-74 | 正常验证强度 | **2 题** | 1 核心 + 1 迁移 |
| **低置信** | <45 | 初步观察，证据薄弱 | **1 题** | 1 核心 |

**阈值常量**（`generatePaper/index.js` 和 `bottleneck-view.js` 必须一致）：
```js
const CONFIDENCE_HIGH_THRESHOLD = 75
const CONFIDENCE_MEDIUM_THRESHOLD = 45
```

### 2.3 无 weight 时的回退（`buildConfidence`）

当卡点没有 weight 字段时（如 candidateBottleneck），用 `evidenceStrength` 映射：
- `high` → weight 85（高置信）
- `medium` → weight 60（中置信）
- 其他 → weight 35（低置信）

## 3. 卡点细颗粒度模型（BN）

### 3.1 两级结构

```
粗卡点（LP，~8个）           细卡点（BN，~38个）
├── LP-001 计算错误           ├── BN-DEC-MUL-POINT-COUNT 小数位数累计
│                             ├── BN-DEC-DIV-POINT-MOVE 小数点移动
│                             └── ...（共 10 个 BN）
├── LP-002 分数运算           ├── BN-FRACTION-ADD-COMMON 通分错误
│                             └── ...（共 7 个 BN）
├── LP-004 单位换算           └── ...（共 10 个 BN）
└── ...
```

### 3.2 验证卷按 BN 出题

验证卷的每个 target 是一个**细卡点（BN）**，不是粗卡点（LP）。
38 个 BN 按置信度分层出题，总题数约 60-80 题。

**禁止**：用 LP 代码作为验证卷 target（会导致每个 LP 只出 2 题，无法覆盖 BN 级别）。

### 3.3 BN 的唯一来源

BN 来自 `profile.currentBottlenecks[].candidateBottlenecks`。
`extractFineBottlenecks(profile)`（`auto-verification.js`）负责展开：
- 读 `pendingBottlenecks` + `currentBottlenecks`（合并去重）
- 展开每个粗卡点的 `candidateBottlenecks` 为 BN 列表
- 无 candidate 的粗卡点用 LP 代码作 fallback（标注 `coarse: true`）

## 4. 诊断报告 ↔ 验证卷 ↔ 反馈 闭环

### 4.1 完整数据流

```
全量诊断（上传试卷）
    ↓
诊断报告（report, type=diagnosis）
  ├── report.bottlenecks = 本次 AI 识别的卡点
  ├── profile.currentBottlenecks = merge 全量历史卡点（不覆盖）
  └── 自动触发 triggerAutoVerificationPaper
        ↓
验证卷（paper, type=verification）
  ├── paper.triggeredByReport = report._id
  ├── paper.bottleneckTargets = 全量 BN（置信度分层出题）
  ├── paper.verificationStatus = 'pending'
  └── report.verificationPaperId = paper._id（双向关联）
        ↓
用户下载 PDF → 打印 → 作答 → 拍照上传
        ↓
验证报告（report, type=verification, paperId 指向 paper）
  ├── 比对每个 BN 的 passed/failed
  ├── paper.verificationStatus = 'completed'
  └── paper.verificationReportId = report._id
        ↓
profile 更新
  passed → status='improved', weight-30/-40
  failed → weight+15
```

### 4.2 关键关联字段

| 字段 | 集合 | 含义 |
|---|---|---|
| `report.verificationPaperId` | reports | 诊断报告关联的验证卷 ID |
| `report.verificationPaperStatus` | reports | 验证卷状态（generating/ready/failed） |
| `paper.triggeredByReport` | papers | 验证卷触发的诊断报告 ID |
| `paper.verificationStatus` | papers | 验证生命周期（pending/completed） |
| `paper.verificationReportId` | papers | 验证完成后关联的验证报告 ID |
| `report.paperId` | reports | 验证报告指向的验证卷（上传作答时写入） |

### 4.3 关键设计原则

1. **诊断报告展示全量卡点**：优先用 `profile.currentBottlenecks`（merge 全量），而非 `report.bottlenecks`（单次）
2. **验证卷覆盖全量 BN**：用 `extractFineBottlenecks` 展开所有 candidateBottlenecks
3. **profile 不被覆盖**：`rebuildSubjectProfile` 用 merge 语义（回放所有有效报告），不取最新一份覆盖
4. **归档保护**：覆盖写之前把旧 `currentBottlenecks` 存到 `archivedBottlenecks`

## 5. 信息一致性全局原则

### 5.1 卡点统计统一口径

**所有页面展示"待修复卡点数"时，必须使用统一口径：**

```
待修复 = status !== 'improved'
       = needs_verification + persisting + recurring + worsened
```

**禁止**：
- ❌ 只数 `persisting`（漏了 needs_verification）
- ❌ 只数 `needs_verification`（漏了 persisting）
- ❌ 用 `pendingBottlenecks.length`（粗卡点未展开）

**实现**：`buildBottleneckStats()` 的 `pendingCount` 和 `activeCount` 都用 `status !== 'improved'`。

### 5.2 各页面一致性要求

| 页面 | 数据源 | 必须一致的指标 |
|---|---|---|
| subject-home（学科工作台） | profile.currentBottlenecks（展开 BN） | pendingTaskCount |
| knowledge-map（学习地图） | profile.currentBottlenecks（展开 BN） | summary 的"X 个待修复" |
| student-profile（学生档案） | profile.currentBottlenecks | knowledgeMapCard.summary |
| report（诊断报告） | profile.currentBottlenecks（优先）| bottleneckCount |
| paper-preview（验证卷预览） | paper.bottleneckTargets | targetCount |

**如果任何两个页面的数字不一致，就是 bug。**

### 5.3 置信度展示统一

所有展示卡点的地方，必须附带置信度标签：

| 展示形式 | 格式 | 示例 |
|---|---|---|
| 紧凑标签 | `●●● 高置信` | `<text class="confidence high">●●● 高置信</text>` |
| 详情行 | `8次证据 · 通过0/失败2` | `confidenceDetail` |
| 分数 | `82分` | `confidence.score` |

数学正式诊断报告采用高密度证据矩阵，同时展示：

| 指标 | 数据来源 |
|---|---|
| 综合置信分 | `weight`，缺失时按 `evidenceStrength` 回退 |
| 出现次数 | `evidenceCount`，只统计最终有效正式诊断 |
| 累计错题 | `cumulativeErrorCount` |
| 最近错题 | `recentErrorCount` |
| 复测结果 | `verificationPassCount` / `verificationFailCount` |
| 首见、最近、持续时间 | `firstSeenAt` / `lastSeenAt` |

细卡点有独立历史指标时展示自己的数字；没有独立指标时明确标注“沿用所属能力卡点统计”，不得推算或伪造细卡点数据。

颜色规范：
- 高置信：红色系（`#c53030` / `#fed7d7`）
- 中置信：黄色系（`#b7791f` / `#fefcbf`）
- 低置信：灰色系（`#718096` / `#e2e8f0`）

### 5.4 历史指标回填

`reanalyzeMathHistory` 提供 `backfillCumulativeErrors` 阶段：

- 只读取数学、正式诊断、已完成且有效的报告。
- 排除重复照片、质量不足、已归档报告和带 `replacedByReportId` 的旧源报告。
- 替代报告按 `reanalysis.sourceReportId` / `originalReportId` 归并，同一来源只保留最终有效版本。
- 按 `bottleneckId || lpCode` 聚合真实 `errorCount`，不使用 `evidenceCount`、`weight` 或乘法估算。
- 默认 dry-run；应用时写入 `metricBackfill.version = math-cumulative-errors-v1`。
- 同版本重复执行覆盖相同聚合结果，不做增量累加。

### 5.5 基础符号白名单

界面只允许以下经过目标设备验证的基础符号：

```text
🗺️ 📚 📄 📸 📊 🎯 ✅
```

符号必须通过 `miniprogram/utils/ui-symbols.js` 的语义键使用，并始终保留文字标题。人物、家庭、肤色、国旗、ZWJ 组合及未验证符号继续禁止。

## 6. 验证卷格式规范

### 6.1 PDF 排版参数

| 参数 | 值 | 说明 |
|---|---|---|
| 纸张 | A4（595×842pt） | 标准 |
| 双栏 | 栏宽 253pt，间距 16pt | 充分利用宽度 |
| 每页 target 数 | 5 个（=10 题） | `DEFAULT_MATH_TARGETS_PER_PAGE = 5` |
| 分页预留 | 65pt | 双栏一行实际 60-70pt |
| 卡点名截断 | 20 字 | 双栏宽度可容纳 |
| 字体 | NotoSansCJKsc-Regular.otf | 中文支持 |

### 6.2 卡点组标题

每个卡点组（同一 BN 的题目）标题格式：
```
A. 小数乘法中积的小数位数判断错误    验证 · 3题·高置信
```
- 左侧：序号 + 卡点名（完整，不截断）
- 右侧：验证强度标注（题数 + 置信度标签）

### 6.3 题目结构

每道题包含：
- `content`：题目内容（带具体数字）
- `answer`：答案
- `explanation`：解题步骤（具体计算过程）
- `questionRole`：`core`（核心题）或 `transfer`（迁移题）
- `lpCode`/`targetId`：绑定的 BN 代码

### 6.4 答案页

独立页面，双栏排版，每题包含：
- 题号 + 卡点名 + 答案
- 解题思路（具体计算过程）

### 6.5 追加模式（`_appendToPaperId`）

当 BN 数量超过单次 LLM 调用限制（~5 个 BN / 55 秒）时，分批生成追加到同一份 paper：
1. 第一批：创建 paper（`_autoPaperId` 或新建）
2. 后续批：传 `_appendToPaperId`，题目追加到同一 paper
3. 最后：调 `_regeneratePdf` 用全部题目重新生成 PDF

**`_regeneratePdf` 必须重建 verificationPack**（重新分页），不能复用旧的分页信息。
