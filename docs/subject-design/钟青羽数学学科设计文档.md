# 钟青羽数学学科设计文档

> 目的：给后续协作开发者或其他 AI 快速理解钟青羽数学学科在本项目中的背景、设计思路、功能列表、数据情况和学习卡点追踪方式。
> 适用范围：微信小程序 `miniprogram-learning-diagnostic` 的数学链路。
> 当前阶段：数学是 MVP 最完整、样本最多、闭环最成熟的学科。

---

## 1. 整套背景

### 1.1 项目背景

本项目最初不是一个“大而全家庭学习 OS”，而是从一个更小、更可验证的闭环收敛出来：

```text
错题
↓
诊断根因
↓
验证假设
↓
认知修复 / 专项练习
↓
重新测试
↓
更新学习卡点状态
```

数学成为第一阶段 MVP 的核心学科，原因是数学卷面具备明确的作答证据：题目、学生答案、演算过程、老师批改、订正痕迹都可以被拍照保存。相比语文和英语，数学尤其需要保留纸笔过程，因为很多问题不在最终答案，而在中间步骤、列式方向、单位处理、验算习惯和多条件管理。

因此，本项目的数学设计采用“纸面证据优先”的策略：

- 孩子在线下纸上作答。
- 家长拍照上传完整卷面。
- AI 识别错题、批改痕迹、订正痕迹和可能根因。
- 系统形成学习卡点。
- 针对学习卡点生成 A4 验证试卷。
- 孩子再次纸笔作答后上传。
- 系统根据清晰、完整、正确的验证证据更新趋势。

### 1.2 钟青羽数学样本背景

项目早期已经在电脑端完成过两轮钟青羽数学试卷分析：

| 项目 | 情况 |
| --- | --- |
| 学生 | 钟青羽，六年级，小升初/初一衔接阶段 |
| 早期材料 | 第一版 38 张图，第二版新增 94 张图 |
| 累计材料 | 30+ 套数学材料，132 张试卷图片 |
| 识别错题 | 80+ 道 |
| 归纳卡点 | 10 大类学习卡点，35+ 个具体实例 |
| 材料类型 | 计算过关练、比与比例专项、综合测试、入学考、分班考、初一衔接卷、应用题专项、几何专题等 |

2026-06-08 更新版报告对早期判断做了重要修正：钟青羽不是“大面积不会数学规则”，而是在综合数学任务中，过程管理、跨表征转换、长链条推理和主动检查不够稳定。

### 1.3 产品术语选择

本项目统一使用“学习卡点”，避免使用“认知缺陷”“Bug”等对家长和孩子更有压力的表达。

“学习卡点”表示：孩子在完成某类题目时反复遇到的具体阻碍环节。它不是负面标签，也不等于能力缺陷，而是一个可以被验证、跟踪和改善的学习线索。

## 2. 设计思路

### 2.1 数学学科的核心假设

数学学习问题可以通过“错题证据”形成可追踪的学习卡点，并通过纸质验证卷进行复测。

系统不追求一次上传就给出绝对结论，而是把 AI 诊断作为“可验证假设”：

```text
一张试卷错题
→ AI 发现可能卡点
→ 多张试卷累计证据
→ 生成验证题确认
→ 验证通过才更新为改善
```

### 2.2 数学为什么不做纯在线答题

数学题的关键证据常常出现在中间过程：

- 竖式是否进位、退位正确。
- 分数、小数、百分数是否转换正确。
- 应用题是否先理清“单位 1”和数量关系。
- 方程中的变量含义是否清楚。
- 几何题是否选对公式和单位。
- 算完后是否回到题意检查。

纯在线选择或填空只能记录最终答案，容易丢失最重要的诊断信息。因此数学第一版采用：

```text
系统出题 / 家长打印
→ 孩子纸笔作答
→ 家长拍照上传
→ AI 结合卷面过程分析
```

### 2.3 页面职责边界

数学链路中的页面分工如下：

| 页面 | 角色 | 不承担什么 |
| --- | --- | --- |
| 学习档案首页 | 展示孩子整体学习摘要、最新报告、重点卡点和学习记录 | 不展开所有数学细节 |
| 数学工作台 | 回答“数学下一步做什么”：拍照诊断、生成验证卷、查看记录 | 不重复大段综合诊断 |
| 诊断报告页 | 展示本次诊断结论、卡点、错题详情、证据来源 | 不做长期趋势全集 |
| 学习卡点中心 | 聚合当前待跟进、持续出现、已改善卡点 | 不展示每张原始照片 |
| 学习卡点详情页 | 展示单个卡点的证据链、报告、验证卷和反馈 | 不替代报告正文 |
| 验证试卷页 | 基于待验证细卡点生成 A4 PDF；手动兜底最多 80 个目标 | 不承载诊断解释 |
| 试卷预览页 | 下载、打印、上传作答反馈 | 不重新生成卡点 |
| 学习记录页 | 按天追溯报告、试卷、反馈、照片/OCR | 不作为主诊断页面 |

### 2.4 AI 诊断的可信度原则

数学报告不是“AI 说了就算”。系统加入了多层约束：

- 图片按批次分析，结果归一化后再合并。
- 疑似重复照片保留在记录中，但不重复计入卡点。
- 报告有质量等级：证据较充分、建议复核、样本不足。
- 家长可以反馈报告、卡点、错题或照片不准确。
- 验证报告只有在“题目完整、作答清晰、全部正确”时，才允许把卡点标记为已改善。

## 3. 程序的功能列表

### 3.1 数学主流程功能

| 功能 | 说明 | 主要页面/云函数 |
| --- | --- | --- |
| 拍照诊断 | 最多上传 20 张数学试卷/作业照片，上传后后台异步分析 | `upload`、`uploadAndAnalyze`、`analyzePhotos` |
| AI 试卷分析 | 调用视觉模型识别错题、学生答案、批改痕迹、订正痕迹和学习卡点 | `analyzeBatch`、`analyzePhotos` |
| 诊断报告 | 展示本次主要结论、错题数、学习卡点、错题详情和证据来源 | `report`、`report-presenter` |
| 学习卡点抽取 | 将错题归入可读短名，如“计算基础”“审题理解”“应用建模” | `bottleneck-taxonomy.js`、`bottleneck-view.js` |
| 学习卡点中心 | 按全部/数学/语文/英语和状态筛选卡点 | `bottleneck-center` |
| 单卡点详情 | 查看某个卡点的证据链、相关报告、验证试卷和反馈 | `bottleneck-detail` |
| 验证试卷生成 | 覆盖待验证细卡点，按置信度 1-3 题分层出题，生成 A4 PDF | `generate-verification`、`generatePaper`、`regenerateVerificationPaper` |
| 默认诊断试卷 | 没有现成试卷时，按年级生成一套综合诊断卷 | `default-paper`、`generatePaper` |
| 试卷预览和下载 | 预览 A4 试卷、下载 PDF、避免重复下载 | `paper-preview` |
| 验证反馈上传 | 孩子做完验证卷后，拍照上传作答，生成验证报告 | `upload?mode=verification`、`analyzePhotos` |
| 学习记录 | 按天聚合诊断报告、验证试卷、验证反馈和原始照片 | `upload-history`、`studentData.getLearningTimeline` |
| 家长纠错反馈 | 对报告、卡点、错题、照片提交反馈，不直接覆盖原始报告 | `reportFeedback` |

## 4. 当前的数据情况

### 4.1 已有历史分析数据

数学是当前项目中真实样本最充分的学科。

| 数据项 | 当前情况 |
| --- | --- |
| 历史分析材料 | 30+ 套数学材料 |
| 历史图片数 | 132 张 |
| 历史错题数 | 80+ 道 |
| 历史卡点类别 | 10 大类 |
| 新增真实小程序数据 | 已在小程序中上传大量真实数学试卷图片，后续以云端 `reports / papers / subjectProfiles / analysisTasks` 为准 |
| 真实报告示例 | 小程序中已出现 2026-06-14 22:53 的数学诊断报告，展示 9 张照片、18 道相关错题、3 条待跟进、2 条持续出现、0 条已改善 |

### 4.2 2026-06-08 更新版的主要判断

新增材料后，数学诊断重点从“单点知识补漏”转向“高负荷综合任务稳定性”：

| 重点方向 | 判断 |
| --- | --- |
| 高负荷多步骤执行 | A 级，高判断强度。长链条题中间结果传递、步骤保存、自检不稳定 |
| 分数/小数/百分数切换 | A 级，高判断强度。跨表征转换和单位 1 判断需要持续验证 |
| 代数表达与方程建模 | A- 级，中高判断强度。已有方程意识，但变量解释、移项、回代不稳 |
| 复杂应用题建模 | A- 级，中高判断强度。简单线性题可完成，高负荷综合题更容易波动 |
| 几何图形分解与公式适用 | B 级，中判断强度。基础图形不是缺失，但组合图形/圆柱等题型需观察 |
| 主动验算与结果合理性检查 | A 级，高判断强度。订正能力较好，但首次作答前检查不足 |

## 5. 学习卡点追踪趋势

### 5.1 趋势不是单次结论

数学卡点追踪以时间序列为核心。系统关心的不只是“这次错了什么”，而是：

- 第一次什么时候出现。
- 最近什么时候还出现。
- 是否在不同试卷中重复出现。
- 是否做过验证卷。
- 验证是否完整、清晰、正确。
- 是否曾经改善后再次出现。

### 5.2 卡点状态

| 状态 | 含义 | 家长侧动作 |
| --- | --- | --- |
| `needs_verification` / 待验证 | 新发现或证据还不足，需要验证 | 生成验证试卷 |
| `persisting` / 持续出现 | 多次报告中反复出现，或验证未通过 | 优先跟进 |
| `improved` / 已改善 | 验证卷中完整、清晰、全部正确 | 继续观察巩固 |
| `recurring` / 再次出现 | 曾经改善，后续又在诊断中出现 | 提高优先级，重新验证 |
| `declining` / 下降中 | 验证证据显示有所改善但仍需观察 | 保持复测 |

### 5.3 趋势字段

`subjectProfiles.currentBottlenecks` 中会逐步沉淀以下信息：

| 字段 | 含义 |
| --- | --- |
| `firstSeenAt` | 第一次出现时间 |
| `lastSeenAt` | 最近一次在诊断中出现时间 |
| `lastVerifiedAt` | 最近一次验证时间 |
| `lastPassedAt` | 最近一次完整通过验证时间 |
| `lastFailedVerificationAt` | 最近一次验证未通过时间 |
| `evidenceCount` | 证据次数 |
| `recentErrorCount` | 最近相关错题数量 |
| `verificationPassCount` | 验证通过次数 |
| `verificationFailCount` | 验证未通过次数 |
| `trend` | `new / persisting / declining / improved / recurring` |
| `weight` | 系统综合优先级权重 |

### 5.4 验证通过的严格规则

数学验证报告只有在满足以下条件时，才允许把某个卡点更新为已改善：

```text
expectedQuestionCount > 0
attemptedQuestionCount === expectedQuestionCount
blankQuestionCount === 0
unclearQuestionCount === 0
incorrectQuestionCount === 0
evidenceStatus === 'passed'
```

空白、模糊、少题、AI 未识别到证据或明确错题，都不能判定为已改善。它们只能进入“证据不足”“仍需验证”或“持续出现”。

### 5.5 给后续 AI 的使用建议

后续 AI 在接手数学链路时，应遵守以下原则：

1. 不要只看单次报告，要结合 `subjectProfiles.currentBottlenecks` 和学习记录时间线。
2. 不要把内部 LP 编号直接展示给家长，应使用短名和解释。
3. 不要把“没有识别到错误”当成“已经改善”。
4. 数学题尽量保留纸笔作答过程，不建议改成纯在线答题。
5. 验证卷应围绕少量高优先级卡点生成，避免一次覆盖过多目标。
6. 对钟青羽当前阶段，优先关注“多步骤执行、跨表征转换、复杂应用建模、主动验算”。
