# 钟青羽验证任务包与分页验证卷设计文档

> 目的：把现有“选择少量学习卡点 → 生成一张验证试卷 → 整卷上传判断”的链路，升级为“系统自动排程 → 生成多页验证任务包 → 每页独立编号 → 分页上传 → 按题/按卡点更新掌握状态”的长期验证系统。
> 适用范围：微信小程序 `miniprogram-learning-diagnostic` 中数学、语文及后续英语纸面验证链路。
> 当前阶段：设计说明 + 执行依据。后续实现以 `docs/archive/superpowers-plans/2026-06-16-verification-task-pack.md` 为准。
> 设计日期：2026-06-16。

---

## 1. 背景与问题

细颗粒度学习卡点上线后，验证卷生成逻辑暴露出结构性问题。

旧逻辑默认一张验证卷最多选择 5 个卡点。这个规则在粗卡点阶段可以接受，因为系统里只有 `计算基础`、`审题理解`、`应用建模` 等少量大类。但数学卡点拆细后，一个孩子可能同时存在 30 个以上待验证细卡点。如果仍让家长手动勾选，就会出现：

1. **选择成本高**：33 个卡点挤在一个列表里，家长很难判断先测哪个。
2. **覆盖不均匀**：每次容易选到前几个高频卡点，后面的卡点长期轮不到。
3. **重复验证**：最近刚测过的卡点可能又被选中，浪费孩子时间。
4. **命中不稳定**：手动选择不一定覆盖真正需要复测的卡点。
5. **一次性负担过大**：如果放开 5 个限制，一份卷可能太长，孩子不可能一次做完。
6. **回传粒度不够**：批量打印后，如果上传照片无法精确对应某一页，就难以判断每个卡点的验证效果。

所以问题不只是“后端上限要不要从 5 改成 10”，而是验证卷需要从“单张试卷”升级成“验证任务包”。

---

## 2. 设计目标

### 2.1 目标

新验证系统要做到：

1. 系统自动排程，减少家长手动挑选。
2. 支持一次生成多页验证任务包，家长可以一次打印。
3. 孩子可以分天、分页完成，不要求一次做完整份 PDF。
4. 每一页都有唯一编号，上传照片后能自动关联到任务包和页。
5. 每道题绑定具体目标：细卡点、知识节点、语文错项或粗卡点。
6. 验证结果按题目聚合，再更新到目标卡点和知识节点。
7. 避免重复验证，保证卡点轮转覆盖。
8. 兼容现有 `papers`、`reports`、`verificationEvidence` 和学习记录页面。

### 2.2 非目标

第一阶段不做：

- 不做复杂二维码识别依赖；先用可 OCR 的页码编号，二维码作为增强项。
- 不强制新增独立集合；可以先把任务包元数据嵌入 `papers`。
- 不一次性重写所有验证报告逻辑。
- 不让孩子在小程序里做在线题；仍以纸面打印和拍照上传为主。
- 不把验证卷变成无限刷题系统；它只用于确认掌握状态。

## 3. 核心概念

### 3.1 验证任务包

验证任务包是一次系统排程生成的验证计划，可以包含多页学生卷和答案页。

示例：

```js
{
  packId: 'VPK-MATH-20260616-01',
  paperId: 'papers_xxx',
  studentId: 'student_xxx',
  subject: 'math',
  status: 'generated',
  totalStudentPages: 8,
  totalTargets: 28,
  totalQuestions: 84,
  generatedAt: Date,
  scheduleStrategy: 'risk_rotation',
  pages: []
}
```

### 3.2 验证页

验证页是孩子实际可以独立完成和上传的最小纸面单位。

示例页码：

```text
MATH-V-20260616-01-P03
```

含义：

| 片段 | 含义 |
| --- | --- |
| `MATH` | 学科 |
| `V` | verification |
| `20260616` | 生成日期 |
| `01` | 当天第 1 个任务包 |
| `P03` | 第 3 页学生卷 |

每页必须清楚打印：

- 任务包编号；
- 页编号；
- 本页覆盖的卡点简述；
- “完成后拍照上传此页”的提示；
- 可选二维码，内容为 pageCode 或上传路由。

### 3.3 验证目标

验证目标是系统想通过题目确认的对象。

目标类型包括：

| 类型 | 示例 | 说明 |
| --- | --- | --- |
| `fine_bottleneck` | `BN-DEC-MUL-POINT-COUNT` | 数学细卡点 |
| `knowledge_node` | `MATH-NUM-DEC-MUL-POINT` | 知识地图节点 |
| `legacy_bottleneck` | `LP-001` | 兼容旧卡点 |
| `chinese_error_item` | `CHI-WORD-BIANLUN` | 语文具体错项 |

每个目标可以被多道题覆盖：

- 核心题：直接验证该卡点；
- 迁移题：观察是否能换情境应用；
- 混合题：观察是否会和相邻知识混淆。

### 3.4 验证题

每道题都要保存结构化元数据，而不是只保存题干和答案。

```js
{
  questionId: 'Q-MATH-V-20260616-01-P03-02',
  pageCode: 'MATH-V-20260616-01-P03',
  index: 2,
  content: '计算：0.24 × 1.5',
  answer: '0.36',
  points: 10,
  targetId: 'BN-DEC-MUL-POINT-COUNT',
  targetType: 'fine_bottleneck',
  lpCode: 'BN-DEC-MUL-POINT-COUNT',
  lpName: '小数乘法中小数位数累计规则不稳',
  questionRole: 'core',
  difficulty: 'medium'
}
```

## 4. 排程策略

### 4.1 从手动选择改为系统推荐

默认入口不再是“勾选 33 个卡点”，而是“生成验证计划”。

系统根据当前学科档案生成候选目标池：

```text
当前细卡点
  + 最近诊断中高频出现的卡点
  + 高置信证据卡点
  + 已改善但需要间隔复测的卡点
  - 最近刚验证过且已通过的卡点
  - 低证据、待重学优先的卡点
```

家长可以调整：

- 今天只生成 2 页；
- 打印完整任务包；
- 暂时跳过某个卡点；
- 只生成某一类，例如“计算类”或“几何类”。

### 4.2 目标排序

建议使用综合分：

```text
score =
  风险权重
  + 最近错误频率
  + 证据强度
  + 距离上次验证的时间
  + 是否复发
  - 最近已通过验证惩罚
  - 已安排在当前任务包惩罚
```

优先级建议：

1. `recurring` 或 `persisting`；
2. 高错误数、高证据强度；
3. 长时间没有验证；
4. 已改善但到达间隔复测日期；
5. 低证据卡点进入微验证，而不是直接进入大卷。

### 4.3 去重与轮转

系统必须避免“永远只测前 5 个”。

规则：

- 同一个 `targetId` 在一个任务包内最多出现一次目标组；
- 最近 3 天已通过的目标默认不再进入任务包；
- 最近 1 次任务包已经安排但未上传的目标，不重复安排；
- 如果卡点数量很多，按领域轮转：计算、几何、应用题、单位换算交替出现；
- 每个任务包保留一部分“回头看”目标，用于间隔复测。

### 4.4 每页容量

不是限制整份卷 5 个卡点，而是限制每页负担。

建议默认：

| 页面类型 | 每页目标数 | 每目标题数 | 每页题数 |
| --- | --- | --- | --- |
| 数学细卡点页 | 2-3 个 | 2-3 题 | 6-8 题 |
| 数学综合复测页 | 3-4 个 | 1-2 题 | 6-8 题 |
| 语文错项页 | 6-10 个具体错项 | 每项 1-2 题 | 8-12 题 |
| 复发专项页 | 1-2 个 | 4-6 题 | 6-8 题 |

孩子可以只做一页。系统不应要求整包一次完成。

## 5. 数据模型

### 5.1 第一阶段：嵌入 `papers`

为降低改造成本，第一阶段仍然使用 `papers` 集合，但新增任务包字段。

```js
{
  _id: 'paper_xxx',
  subject: 'math',
  type: 'verification',
  paperCode: 'MATH-20260616-01',
  paperDisplayCode: '数学-20260616-01',

  verificationPack: {
    packId: 'VPK-MATH-20260616-01',
    mode: 'task_pack',
    scheduleStrategy: 'risk_rotation',
    status: 'generated',
    totalTargets: 28,
    totalQuestions: 84,
    totalStudentPages: 8,
    completedStudentPages: 0,
    pages: [
      {
        pageIndex: 1,
        pageCode: 'MATH-V-20260616-01-P01',
        status: 'pending',
        targetIds: [
          'BN-DEC-MUL-POINT-COUNT',
          'BN-DEC-DIV-POINT-MOVE'
        ],
        questionIds: [
          'Q-MATH-V-20260616-01-P01-01'
        ],
        uploadedReportId: '',
        lastUploadedAt: null
      }
    ]
  },

  questions: []
}
```

### 5.2 第二阶段：独立集合

当分页上传和任务状态稳定后，可以拆出：

| 集合 | 用途 |
| --- | --- |
| `verificationTaskPacks` | 任务包主记录 |
| `verificationPages` | 单页任务状态 |
| `verificationQuestionEvidence` | 逐题证据 |

但第一阶段不强制拆集合，避免让数据库和权限一起膨胀。

### 5.3 reports 增强字段

验证照片上传后，`reports` 增加页级信息：

```js
{
  type: 'verification',
  paperId: 'paper_xxx',
  verificationPageCodes: [
    'MATH-V-20260616-01-P03'
  ],
  verificationPageResults: [
    {
      pageCode: 'MATH-V-20260616-01-P03',
      matchedBy: 'ocr',
      confidence: 0.92,
      targetIds: [],
      questionEvidence: []
    }
  ],
  verificationEvidence: []
}
```

### 5.4 逐题证据

```js
{
  questionId: 'Q-MATH-V-20260616-01-P03-02',
  pageCode: 'MATH-V-20260616-01-P03',
  targetId: 'BN-DEC-MUL-POINT-COUNT',
  targetType: 'fine_bottleneck',
  expectedAnswer: '0.36',
  studentAnswer: '0.36',
  correctness: 'correct',
  evidenceStatus: 'clear',
  reason: '答案正确，过程可见'
}
```

## 6. 流程设计

### 6.1 生成流程

```text
进入生成验证计划
  ↓
读取 subjectProfile / 最近 papers / 最近 reports
  ↓
构建候选目标池
  ↓
排程：选择本任务包目标
  ↓
分页：目标分配到 pages
  ↓
按页生成题目
  ↓
给每页分配 pageCode 和 questionId
  ↓
渲染 PDF：学生页 + 答案页
  ↓
保存 papers.verificationPack
```

### 6.2 完成流程

```text
孩子完成第 3 页
  ↓
家长拍照上传
  ↓
OCR 识别 pageCode
  ↓
根据 pageCode 找到 paper 和 page
  ↓
AI 按该页 questionIds 判题
  ↓
生成 questionEvidence
  ↓
聚合到 targetEvidence
  ↓
更新 reports.verificationEvidence
  ↓
更新 paper.verificationPack.pages[P03].status
  ↓
更新 subjectProfile.currentBottlenecks / chineseReviewItems / studentNodeMastery
```

### 6.3 无法识别页码时

如果 OCR 没有识别出 pageCode：

1. 如果上传入口已经带 `paperId`，优先用 `paperId` 缩小范围；
2. 根据题干相似度匹配 `questions`；
3. 匹配置信度低时，报告标记为 `needs_review`，不更新掌握状态；
4. 页面提示家长重新拍清楚右上角编号。

## 7. 页面体验

### 7.1 生成验证计划页

当前 `generate-verification` 页面应从“勾选卡点列表”改为：

1. 顶部展示本次推荐：
   - 覆盖多少个卡点；
   - 预计多少页；
   - 建议分几天完成；
   - 本次排程策略。
2. 展示分页计划：
   - 第 1 页：小数乘法、小数除法；
   - 第 2 页：面积单位换算、平方千米与公顷；
   - 第 3 页：百分数与小数互化、抄写检查。
3. 每页可展开看题目目标。
4. 家长可以：
   - 生成今日 2 页；
   - 生成完整任务包；
   - 暂时移除某一页；
   - 进入高级手动选择。

### 7.2 试卷预览页

`paper-preview` 增加：

- 任务包进度：`已完成 2/8 页`；
- 页列表；
- 每页状态：未完成、已上传、已通过、需补做、图像不清；
- 上传按钮支持“上传某一页”。

### 7.3 学习记录页

学习记录中，验证任务包是一条主记录，分页上传作为折叠子记录：

```text
数学验证任务包 数学-20260616-01
覆盖 28 个卡点，共 8 页，已完成 3 页
  - 第 1 页 已通过
  - 第 2 页 未通过 2 个卡点
  - 第 3 页 图像不清
```

## 8. AI 输出要求

生成题目时，AI 不只返回 `questions`，还要返回页结构或可由后端稳定分页。

建议输出：

```js
{
  title: '数学验证任务包',
  pages: [
    {
      pageTitle: '第 1 页：小数乘除专项',
      targetIds: ['BN-DEC-MUL-POINT-COUNT'],
      questions: []
    }
  ]
}
```

短期兼容策略：

- 后端先自行分页；
- AI 仍返回 `questions`；
- 后端根据 `targetId`、`questionRole` 和容量规则生成 `verificationPack.pages`；
- 等分页稳定后再要求 AI 原生返回 pages。

## 9. 验证证据规则

每个目标的状态不再只看整张卷，而是看该目标对应题目的证据。

| 状态 | 判断 |
| --- | --- |
| `passed` | 该目标所有预期题都清晰作答且正确 |
| `failed` | 任一核心题错误 |
| `partial` | 迁移题错误但核心题正确 |
| `incomplete` | 有空白或缺少题目 |
| `unclear` | 图像不清无法判断 |
| `missing` | 未上传对应页 |

数学掌握状态建议：

- 核心题全对、迁移题全对：提升掌握置信度；
- 核心题错：卡点仍然存在；
- 迁移题错：标记为部分掌握，安排相邻知识节点复测；
- 页未上传：不更新掌握状态，只更新任务包进度。

语文错项状态仍按三次间隔复测规则：

- 一次通过只升 interval；
- 三次间隔通过才 `mastered`；
- 任意失败进入 `recurring`。

## 10. 实施阶段

### Phase 1：任务包排程与分页元数据

- 新增纯函数：从当前卡点生成目标池；
- 新增纯函数：将目标分配到页；
- 为题目补 `questionId`、`pageCode`、`targetId`、`targetType`、`questionRole`；
- `papers` 写入 `verificationPack`；
- 不改大 UI，只保证数据结构存在。

### Phase 2：PDF 打印页码

- PDF 每个学生页右上角打印 `pageCode`；
- 页脚显示 `第 x/y 页`；
- 答案页按 `pageCode` 分组；
- 测试 PDF 渲染函数返回页码元数据。

### Phase 3：生成页面升级

- `generate-verification` 页面从卡点选择改成验证计划预览；
- 默认显示系统推荐页；
- 保留高级手动选择；
- 去掉“整份卷最多 5 个卡点”的产品限制，改成每页容量限制。

### Phase 4：分页上传与匹配

- 上传验证卷时允许只上传一页；
- OCR 识别 `pageCode`；
- 识别失败时回退到 `paperId + 题干匹配`；
- 匹配不到则报告标记为证据不足。

### Phase 5：证据聚合与掌握状态

- `verification-evidence` 按 `questionId` / `targetId` 聚合；
- 更新 `verificationPack.pages.status`；
- 更新 `subjectProfiles.currentBottlenecks`、`chineseReviewItems`；
- 数学后续更新 `studentNodeMastery`。

### Phase 6：任务包进度展示

- 试卷预览页展示页进度；
- 学习记录页折叠展示任务包与分页结果；
- 报告页显示本次只验证了哪些页和哪些目标。

## 11. 验收标准

第一阶段完成后：

1. 生成一份验证卷时，`papers.verificationPack` 存在；
2. 每个学生页有稳定 `pageCode`；
3. 每道题有 `questionId`、`targetId`、`targetType`；
4. 生成 30 个细卡点时，系统能自动分页，而不是只选 5 个；
5. 原有旧卡点验证卷仍能生成；
6. 语文错项验证卷仍优先覆盖具体错项；
7. 全量测试通过。

完整阶段完成后：

1. 家长可一次打印多页任务包；
2. 孩子可只做其中一页；
3. 上传一页照片即可关联到对应 `pageCode`；
4. 验证报告能只更新该页覆盖的目标；
5. 未上传页不会被误判为失败或改善；
6. 同一个细卡点不会在短时间内被反复安排；
7. 卡点覆盖进度可在试卷预览和学习记录中查看。

## 12. 与现有设计的关系

本设计不推翻以下既有设计：

- 数学知识地图与资源库；
- 数学细颗粒度卡点；
- 语文具体错项；
- 现有拍照诊断报告；
- 现有验证报告证据规则。

它主要替换的是“验证卷生成和回传”的组织方式。

旧系统里的“验证试卷”是一张卷；新系统里的“验证试卷”是一组可分批完成的任务页。对家长来说，它仍然是可以打印的 PDF；对系统来说，它是可追踪、可分段、可轮转的验证任务包。
