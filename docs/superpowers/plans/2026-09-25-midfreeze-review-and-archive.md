# 项目中期冻结完整复审与封存计划

## 目标

对现有 Learning Diagnostic 产品在**既定范围内**做一次可追溯的完成度审查，盘清功能、证据、工程、竞品差距和知识资产；修复确认属于遗漏或质量债务的项目内事项，保留历史决策与证据，最终给出继续收尾、冻结维护或归档的明确结论。不得借复审扩大到 AI Learning OS、商业化平台或新的学科/学习场景。

## 已知基线与前置状态

- 工作区仓库没有 remote；依工作区章程，知识库仓库本地保存、永不推送。
- 小程序独立仓库 `main` 已 fetch `origin`，HEAD 与 `origin/main` 同为 `47dde4f`；分支未设置 upstream，裸 `git pull` 因此失败，fetch 已确认没有待合并提交。
- `HANDOFF.md` 记载仍有订阅消息发送链实施、真实标注集评测、学习科学条目提炼和数学竞品矩阵等遗留；复审须逐项对照现行代码和证据重新核实，不能直接沿用旧交接判断。
- 工作区治理以 `00-知识库/00-治理/知识库章程-v1.0.md` 为准；素材区包含隐私资料，归档目录只进不出且不删除。

## 范围

### 纳入

1. 当前产品边界与 PRD/MVP 验收：数学诊断验证闭环、语文具体错项复习、英语词汇熟练度闭环、家庭/多孩流程、隐私与数据控制。
2. 代码、数据模型、AI/评测、可用性、可访问性、稳定性、安全与隐私、运维/发布、文档和质量门禁的完整性与风险审查。
3. 内部文档、计划、决策、里程碑、测试与发布证据、知识库/素材索引、重复和过期资产的清点；审计需要时只提出归档/改名建议。
4. 竞品按产品类别建立可复核市场地图：拍照批改/搜题/错题工具、AI 学习助手、学习机/硬件生态、诊断/学情分析平台、英语词汇工具。列明截至日期、官方来源、产品定位、核心工作流、证据强弱、与本项目相同/不同之处和仅在现有范围内可吸收的改进点。
5. 每个发现形成证据、影响、优先级、建议、估算/依赖和处置状态；区分必须收尾、范围内可选优化、平台/外部依赖、明确不做。

### 排除

- 新增面向用户的学科、年龄段、商业化、教师/机构产品、AI Learning OS 或其他新业务能力。
- 仅为追赶竞品而增加功能；未经证据支持的宣传指标；将未验证的 AI 诊断能力描述为已证明。
- 删除文件/目录、Git 历史、学生素材或备份；任何数据库 schema/数据迁移；修改密钥、CI/CD 或生产部署。
- 将包含隐私的素材上传到 GitHub、报告或外部服务。

## 工作阶段与交付

### A. 冻结基线与证据盘点

- 保存两个仓库状态、分支/提交、工作区布局、运行时和发布配置基线。
- 建立当前能力到 PRD/验收条件、代码入口、测试和用户可见证据的追踪矩阵。
- 清点 roadmap、spec、plan、decision、CHANGELOG、release/test reports，按时间重建从问题/假设到设计、实现、验证、取舍的演进时间线；标识断档与相互冲突。
- 读取清单内每个区的资产并逐项判定：权威、仍有效、需更新、历史保留、重复、未归属或隐私敏感。

### B. 全面内部审查

- 按产品主流程及三学科逐条复核需求覆盖、边界一致性、失败/空/边缘状态和手工验收证据。
- 检查前端/云函数模块边界、鉴权与数据隔离、数据生命周期/删除、隐私暴露面、AI 输入输出校验、重试/超时/幂等/错误可观测性、依赖/体积/性能、无障碍和微信平台兼容性。
- 对照自动化测试、真实数据评测、E2E、部署烟测与 release gate，区分测试覆盖率与实际诊断有效性证据。
- 检查所有活跃文档对代码、基线、相互链接、状态/日期和单一事实来源的准确性；历史材料只校正索引和状态，不改写其当时记录。

### C. 竞品比较与范围内建议

- 以截至审查日的可访问官方产品页面/帮助文档/应用商店资料为首要证据，外部报道仅作补充；标记无法核验或需要实测的主张。
- 类别地图必须覆盖当前产品直接竞争及替代方案；“市场全量”不作无法证实的承诺，报告会列出搜索范围、纳入规则、代表产品及未覆盖边界。
- 按拍照与 OCR、题目/错因诊断、证据追踪、针对性复测、知识掌握状态、家长行动支持、学科闭环、隐私信任、质量证据、平台可达性和使用成本比较。
- 仅推荐可加强当前诊断闭环的改进；每项指出它解决的现有失败/遗漏、竞品证据、成本/风险与不改变范围的理由。

### D. 整理、知识沉淀与归档准备

- 先修复权威索引、状态、链接、版本和重复事实，再处理明确无损的组织调整。
- 完成知识库待提炼条目、竞品/行业复核与工程教训回灌；制作完整资产清单、决策日志和里程碑/演进索引。
- 任何移动、重命名或清理在改动前更新章程/索引和资产映射；被取代内容保留在归档，禁止删除。
- 逐项核实 `.backup-shared-refactor`、`.worktrees`、临时输出及其他疑似遗留目录的来源、当前引用和复现价值；没有明确可追溯结论的保留并登记，不擅自清理。
- 记录外部依赖与封存之后的维护条件（平台/模型变更、隐私请求、数据删除、故障响应、域名/云环境可访问性、备份与恢复责任）。

## 验收门槛与决策

1. 所有既定范围验收条目有代码/文档/测试/实机证据，或明确标记未完成及其阻塞原因；不得以测试通过代替真实学习效果证据。
2. 竞品结论可追溯至截至日期的来源，未核实主张显式标记；优化建议都有优先级、成本和范围判定。
3. 关键决策、计划、里程碑、验证报告和知识条目组成一条可导航的演进脉络；活跃文档不相互冲突，链接门禁通过。
4. 整理记录不丢历史、不触碰隐私红线；高风险遗留和外部依赖有责任与处置状态。
5. 当前可做且在范围内的必要工作完成并通过项目既有文档/测试/部署门禁后，才建议“封存”；否则给出有序的剩余工作清单和停止条件。
6. 封存决定分为：**可封存并停止开发**、**完成明确阻塞项后封存**、**暂不封存**，附支持证据、残余风险、维护模式和复开条件。

## 用户确认与高风险动作

本计划获批后可进行审查、只读核验、文档修订、知识沉淀和非破坏性整理。以下仍须逐项遵守现行红线：删除任何文件/目录、数据库 schema/迁移、修改密钥或 CI/CD、生产部署、改写历史或强制推送需单独确认。工作区知识仓库只本地提交；小程序仓库按项目规则提交并推送。

## 当前状态

计划状态为 `proposed`，等待用户批准后进入审查阶段。批准之前不执行项目代码/文档清理，也不作封存结论。
