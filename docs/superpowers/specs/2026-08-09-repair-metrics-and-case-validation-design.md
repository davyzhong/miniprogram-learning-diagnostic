# 修复率指标页与案例验证波 设计文档

> 日期：2026-08-09
> 状态：ACTIVE（已获用户确认）
> 背景：项目审计确认"修复率统计缺失、真实案例规模不足"是产品层仅剩的两个 gap。本设计覆盖第 1 波（产品验证波）：修复率指标页 + 3-5 个真实孩子案例验证 + Go/No-Go 决策。

## 1. 目标

1. 把北极星指标"修复率"落地为**家长可见的完整指标页**（用户明确选择，非仅内部工具）。
2. 组织 3-5 个真实孩子的案例验证，积累 ≥10 条卡点记录。
3. 按原规划阈值产出 Go/No-Go 决策依据。

核心假设（全项目一以贯之）：学习中的卡点可以被发现、定位、改善和复测。本波就是第一次真正检验它。

## 2. 指标定义与口径（仅数学）

双指标并列：

| 指标 | 公式 | 回答的问题 |
|------|------|-----------|
| 验证覆盖率 | 有验证证据的卡点 / 档案中全部卡点 | 闭环用起来了没有 |
| 严格修复率 | 修复后复测通过的卡点 / 完成过修复动作的卡点 | 修复到底有没有效（北极星） |

口径定义：

- **验证证据** = 微验证会话通过（`microValidations` 判定 ≥2/3 题对）**或** 验证卷作答被判 improved（`verification-evidence.js` 证据分态 passed）。两条链都算。
- **修复动作完成** = 该卡点的任务包完成（`learningResourcePacks`）**或** 干预会话完成（`interventionSessions`）。
- **修复后复测通过** = 复测证据的时间戳晚于修复动作完成时间。早于修复动作的验证证据不计入严格修复率分子（防止把"没修就自己好了"算成修复成功）。
- **小样本保护**：任一指标分母 < 5 时数字照算，页面标注"样本不足，结论仅供参考"。Go/No-Go 不允许建立在小样本上。
- **学科范围**：仅数学。语文无细卡点体系、英语是词汇自洽闭环，均不进此指标。

卡点去向四档分类规则（互斥，按优先级判定）：

1. **已修复** = 有修复后复测通过的证据
2. **修复中** = 已发起修复动作（任务包或干预会话存在），但尚无通过的复测证据
3. **已验证未通过** = 有验证证据但从未通过，且未发起修复动作
4. **未验证** = 无任何验证证据

## 3. 页面设计

新增分包页 `repair-metrics`（学习修复指标页）。

入口（2 个）：

- 数学学科工作台（subject-home）
- 家庭工作台（index）

页面结构（自上而下）：

1. **双指标卡片**：验证覆盖率 / 严格修复率，各含分子/分母数字。
2. **口径说明**：一句话摘要，可展开看完整定义。
3. **卡点去向分布**：已修复 / 修复中 / 已验证未通过 / 未验证 四档计数 + 列表。复用 `bottleneck-view.js` 展示规范；遵守质量红线，不暴露 LP/BN 等内部编码。
4. **时间快照**：按验证证据日期聚合的修复率变化。实时从证据时间戳现算，不建事件集合。
5. **小样本提示条**：任一指标分母 < 5 时显示。

## 4. 数据流与接口

- 云函数：`studentData` 新增 action `getRepairMetrics(studentId)`。
- 权限：沿用现有 `access.js` 校验（owner / co-parent viewer 均可读）。
- 读取集合：`subjectProfiles`、`microValidations`、`learningResourcePacks`、`interventionSessions`、`reports`（验证报告证据）。
- **纯只读**：不写任何集合，不新增集合（方案 A：实时聚合，零新增写入）。
- 返回包络遵循 `{success, data, error}`；前端 `timeout: 60000` 不适用（无 LLM 调用，默认超时即可）。

## 5. 案例验证流程（线下为主）

产出物 1 —— 招募材料（放知识库 `03-产品商业与传播/`）：

- 一页介绍：给家长讲清楚参与内容、能得到什么、隐私如何处理。
- 微信招募消息模板：面向熟人/同事家长圈（用户确认的唯一渠道）。

每家庭流程：

1. 提供 3 道真实错题
2. 拍照诊断 → 确认卡点
3. 任务包/干预（"学一下"）
4. 微验证或验证卷复测
5. 记录进案例表

产出物 2 —— 案例记录模板（放本地知识库 `06-案例验证/`）：

- 脱敏编号记录：孩子年级 / 错题主题 / 卡点 / 修复动作 / 复测结果 / 时间。
- 真实姓名与信息只留本地，不入 Git（隐私红线）。

时间盒：

- 招募 2 周 + 执行 2 周。
- 招不满 3 个家庭则降为 2 个，并在最终报告明确标注样本量。

## 6. Go/No-Go 决策机制

- 阈值沿用原规划：修复率 <30% 闭环可能无效；30-50% 方向有效；50-70% 价值明显；>70% 核心假设很强。
- 前置条件：累计 ≥10 条进入验证流程的卡点记录，且严格修复率分母 ≥5（脱离小样本）。
- 结束时产出《案例验证报告》：
  - 脱敏版进 `docs/test-reports/`（随代码提交）
  - 含真名细节版只留本地知识库 `06-案例验证/`

## 7. 测试策略

- `getRepairMetrics` 聚合逻辑单测：覆盖各状态组合、修复/复测时间先后判定、小样本分支、空档案分支。
- `repair-metrics` 页 page-flows 测试（按页面拆分的现有模式）。
- 内部编码红线测试：断言页面可见文本不匹配 `/^(LP|BN|CHI|ERR|MATH)-/`（现有 user-facing-code-hygiene 模式）。

## 8. 边界与不做

- 不新增任何数据库集合（趋势用证据时间戳现算）。
- 不做语文/英语修复率。
- 不做应用内案例管理模块（案例记录用本地模板，纯线下）。
- 不做修复率推送/订阅消息（订阅消息本身仍是 Deferred 项）。
- 招募不投放公开渠道（仅熟人圈）。
