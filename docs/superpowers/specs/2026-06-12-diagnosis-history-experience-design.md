# 综合诊断与历史报告体验设计

**日期**: 2026-06-12
**状态**: 已确认
**适用阶段**: 单人 MVP，钟青羽数学学科

## 1. 目标

重新设计学科主页、综合诊断与单次报告的阅读体验，让家长能够顺利完成：

```text
上传试卷 → AI 分析 → 阅读本次报告 → 理解当前卡点 → 生成验证试卷
```

本阶段优先保证主线清晰、判断可靠、历史可追溯。数据量和诊断报告数量显著增加后，再考虑复杂趋势分析、诊断可信度和能力评估。

## 2. 当前问题

当前学科主页将多份历史报告以相似卡片依次展示，存在以下问题：

1. 家长无法从列表中快速理解孩子当前最需要关注什么。
2. 多份报告彼此独立，没有形成最新的综合判断。
3. 点击报告后，直接阅读报告正文的路径不够清晰。
4. 历史记录展示“有多少份报告”，但没有说明每次报告带来了什么变化。
5. 分析中、失败、重复照片等状态可能干扰当前可靠结论。

## 3. 产品原则

### 3.1 唯一阅读主线

面向家长只保留：

```text
当前结论 → 最近变化 → 单次报告
```

“诊断证据”“可信度”“OCR 结果”等概念不进入主界面。用户需要进一步理解时，再进入具体卡点、试卷或图片查看。

### 3.2 当前结论与历史事实分离

- **综合诊断**保存现在的最新可靠结论，可以持续更新。
- **单次报告**保存当次分析事实，完成后永久保留，不随综合诊断变化而改写。

### 3.3 可靠优先于完整

系统宁可暂时显示“需要验证”，也不能根据普通试卷中未出现卡点、重复照片或低质量识别结果判断“已有改善”。

### 3.4 一个状态，一个主要行动

每种页面状态只突出一个最适合的下一步，减少家长决策负担。

## 4. 信息架构

### 4.1 学科主页：当前综合诊断

页面依次展示：

1. **当前最需要关注**：一段简短结论，说明重点卡点和建议顺序。
2. **学习卡点**：展示当前卡点及其状态。
3. **最近变化**：展示最近三次有效报告带来的变化。
4. **主要行动**：生成下一套验证试卷。
5. **功能入口**：拍照诊断、上传历史等原有能力继续保留。

点击“最近变化”直接进入对应单次报告。点击“查看全部历史记录”进入按时间排列的完整报告列表。

### 4.2 单次报告：直接阅读

报告正文在小程序内直接展示，不要求先下载 PDF。

报告仅保留三个主要内容区块：

1. **本次诊断结论**：说明本次新增、再次出现或通过验证的结果，以及建议行动。
2. **发现的学习卡点**：卡点名称、当前状态和简短表现说明。
3. **本次使用的试卷**：可进入查看原始图片。

底部提供：

- 下载 PDF
- 生成验证试卷

### 4.3 历史记录

历史记录按时间倒序展示，不增加诊断/验证筛选 Tab。

每条记录标题使用变化描述，而不是统一显示“诊断报告”，例如：

- 发现分数运算卡点
- 单位换算已有改善
- 应用题建模再次出现

辅助信息显示日期和简短原因。点击后直接进入对应单次报告。

## 5. 卡点状态模型

面向家长仅展示三种状态：

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 需要验证 | 已发现相关表现，但信息不足以确认稳定性 | 首次在有效诊断中发现 |
| 持续出现 | 卡点在不同有效记录中再次出现 | 同一卡点在另一份有效诊断或验证报告中再次出现 |
| 已有改善 | 针对该卡点的验证题已通过 | 只有针对性验证通过才可进入 |

状态更新规则：

1. 首次发现：`需要验证`
2. 再次出现：`持续出现`
3. 针对性验证通过：`已有改善`
4. 改善后再次出现：重新变为 `持续出现`，历史改善记录仍保留

普通诊断中没有发现某卡点，不能将其标记为已有改善。

MVP 中，“针对性验证通过”必须同时满足：

1. 报告关联验证试卷，且该卡点属于本次 `bottleneckTargets`。
2. 该卡点对应的验证题均能明确识别题目、学生答案和正确答案。
3. 该卡点对应的验证题全部答对。

只要存在空白、图片模糊、OCR 无法确认或题目未覆盖，就继续保留原状态，不判断改善。

## 6. 数据设计

本阶段继续使用现有集合，不新增趋势、证据或事件集合。

### 6.1 `subjectProfiles`：综合诊断

保存当前最新可靠结论，包括：

- 当前重点卡点
- 每个卡点的当前状态
- 当前综合摘要
- 下一步建议
- 最近一次有效更新时间

现有 `pendingBottlenecks`、`improvedBottlenecks` 等结构可在实施阶段扩展或归一化，但应由服务端统一生成前端所需视图，避免前端自行推理。

最小新增字段：

```javascript
{
  currentSummary: String,
  currentBottlenecks: [{
    lpCode: String,
    lpName: String,
    status: 'needs_verification' | 'persisting' | 'improved',
    firstSeenAt: Date,
    lastSeenAt: Date,
    sourceReportId: String
  }],
  nextAction: String,
  latestEffectiveReportId: String,
  diagnosisUpdatedAt: Date
}
```

`pendingBottlenecks` 与 `improvedBottlenecks` 在兼容期继续保留，写入时由同一服务端函数同步更新，前端新版页面只读取 `currentBottlenecks`。

### 6.2 `reports`：单次报告

保存当次事实，包括：

- 本次结论摘要
- 相较当前综合诊断发生的变化摘要
- 本次识别到的学习卡点
- 错题详情
- 试卷图片与 OCR 摘要
- 报告类型、状态和 PDF

有效报告完成后不再改写其诊断结果；按需生成 PDF 时，仅允许补充 `pdfFileId` 等派生字段。

最小新增字段：

```javascript
{
  isEffective: Boolean,       // 是否允许参与综合诊断和最近变化
  changeSummary: String,      // 面向家长的一句话变化描述
  profileAppliedAt: Date      // 已成功应用到综合诊断的时间
}
```

`status='completed' && isEffective=true && profileAppliedAt` 存在的报告，才允许进入学科主页“最近变化”。

### 6.3 `papers`：验证任务

继续保存验证试卷及目标卡点。验证答卷上传后仍生成一份 `reports` 记录，并按同一更新流程处理。

### 6.4 最近变化

本阶段不单独存储事件流。学科主页的“最近变化”直接读取最近三份有效报告的变化摘要。

### 6.5 旧数据兼容

上线时不要求一次性迁移全部历史报告：

- 旧报告没有 `isEffective` 时，已完成且包含有效卡点或错题的记录视为有效。
- 旧报告没有 `changeSummary` 时，使用现有 `comparisonSummary`；仍为空时回退到 `summary`。
- 旧学科档案没有 `currentBottlenecks` 时，由服务端根据现有 `pendingBottlenecks` 和 `improvedBottlenecks` 生成兼容视图。
- 新版写入流程启用后，所有新报告必须写入完整的新字段。

历史兼容逻辑集中在服务端读取层，前端不区分新旧数据。

## 7. 更新流程

一次分析完成后，系统只执行三个业务步骤：

```text
保存本次报告 → 对比当前综合诊断 → 更新综合诊断
```

详细流程：

1. 分析生成本次卡点、错题和摘要。
2. 判断本次记录是否有效，是否允许更新综合诊断。
3. 将本次结果与更新前的综合诊断进行对比，生成变化摘要。
4. 将本次完整结果和变化摘要写入单次报告。
5. 根据状态规则更新 `subjectProfiles`。
6. 回写报告的 `profileAppliedAt`。
7. 学科主页读取新的综合诊断和最近三份已应用的有效报告。

对比基准必须是**更新前**的综合诊断，避免本次结果与自身比较。

## 8. 不更新综合诊断的情况

以下情况保留上传和报告记录，但不改变综合诊断：

| 情况 | 页面表现 | 允许保留 | 禁止行为 |
|---|---|---|---|
| 全部图片重复 | 未产生新诊断 | 上传记录、图片 | 不新增卡点，不判断改善 |
| 图片无法识别或有效题目过少 | 信息还不够 | 报告、图片、识别结果 | 不更新当前结论 |
| 普通诊断中未发现历史卡点 | 正常展示本次发现 | 本次报告 | 不判断该卡点改善 |
| 分析中 | 正在分析 | 上一次综合诊断 | 不展示半成品结论 |
| 分析失败或超时 | 分析未完成，可重新分析 | 图片、上传记录、上一次综合诊断 | 不清空或误改综合诊断 |

## 9. 页面状态与主要行动

| 状态 | 核心文案 | 主要行动 |
|---|---|---|
| 尚无诊断 | 上传第一份数学试卷 | 拍照诊断 |
| 只有首次发现 | 已发现需要验证的卡点 | 生成验证试卷 |
| 暂未发现明显卡点 | 本次试卷表现较稳定，仍可继续观察 | 继续上传试卷 |
| 分析中 | AI 正在分析，可以稍后回来查看 | 查看当前综合诊断 |
| 分析失败 | 照片不会丢失，当前综合诊断不受影响 | 重新分析 |
| 全部重复 | 这些照片此前已经分析过 | 查看上传历史 |
| 有稳定结论 | 当前最需要关注的卡点与建议 | 生成验证试卷 |

所有错误信息面向用户只说明：

1. 发生了什么
2. 数据是否保留
3. 下一步做什么

不得展示任务 ID、错误栈或模型内部信息。

## 10. 服务边界

### 10.1 服务端负责

- 判断报告是否有效
- 对比更新前的综合诊断
- 生成变化摘要
- 按状态规则更新卡点
- 保证单次报告与综合诊断写入的一致性

### 10.2 前端负责

- 展示服务端提供的综合诊断
- 展示最近变化和单次报告
- 根据明确状态显示一个主要行动
- 不自行推断卡点状态或改善结果

## 11. 一致性与失败处理

MVP 阶段同一学生、同一学科只允许存在一个活动分析任务。已有任务分析中时，新上传可以保存照片，但必须等待当前任务结束后再启动分析，避免并发报告以不同顺序更新同一份综合诊断。

理想写入顺序：

1. 完成本次报告内容与变化摘要
2. 更新综合诊断
3. 将报告标记为可展示的有效完成状态

若运行环境无法提供跨集合事务，则使用幂等更新和可恢复步骤：

- 每次综合诊断更新记录来源 `reportId`
- 同一 `reportId` 重试时不得重复累计卡点或报告数量
- 若报告完成但综合诊断更新失败，重试应只补做综合诊断更新
- 前端只读取已经成功应用到综合诊断的有效报告作为“最近变化”
- `latestEffectiveReportId === reportId` 或报告已有 `profileAppliedAt` 时，更新流程必须安全返回，不能再次累计

## 12. 测试与验收

### 12.1 状态规则测试

- 首次发现进入“需要验证”
- 同一卡点再次出现进入“持续出现”
- 普通报告未发现历史卡点时不得进入“已有改善”
- 只有目标卡点的有效验证通过才进入“已有改善”
- 验证题存在空白、模糊、无法识别或未全部答对时不得进入“已有改善”
- 改善后再次出现时回到“持续出现”

### 12.2 数据一致性测试

- 同一报告重复处理不重复更新综合诊断
- 更新失败后重试能够恢复
- 变化摘要使用更新前的综合诊断生成
- 单次报告完成后诊断内容不可被后续综合结论覆盖
- 旧报告和旧学科档案能够通过服务端兼容视图正常展示
- 同一学科存在活动分析时，不允许另一分析任务并发更新综合诊断

### 12.3 页面流程测试

- 无数据、数据不足、正常结论、分析中、失败、全部重复均展示正确主行动
- 学科主页点击最近变化直接进入对应报告
- 单次报告无需下载即可完整阅读
- 报告可进入原始试卷并可下载 PDF
- 异常状态下仍可阅读上一次可靠综合诊断

### 12.4 MVP 验收标准

家长能够顺利完成：

```text
上传试卷 → 阅读报告 → 理解当前卡点 → 生成验证试卷
```

同时满足：

- 不丢失历史报告和上传图片
- 不因重复、识别失败或普通诊断缺失而误判改善
- 当前综合诊断始终来自最近一次可靠更新
- 页面不依赖复杂趋势图或技术指标才能理解

## 13. 本阶段不做

- 复杂趋势图和多维筛选
- 诊断可信度分数
- 能力评分或掌握度评分
- 自动学习规划
- 跨学科综合分析
- 新增独立趋势、证据或事件集合

当有效报告数量和验证样本显著增加后，再评估是否引入复杂分析。

## 14. 视觉与交互语言

### 14.1 总体方向

采用“图标 + 少量插图”的视觉方向，在不改变唯一阅读主线的前提下增加活力和亲切感。

- **图标负责识别与操作**：帮助用户快速理解状态、入口和按钮。
- **插图负责情绪与引导**：用于欢迎、等待和空状态。
- **文字负责准确判断**：所有诊断结论必须使用明确文字表达，不能只依赖颜色、图标、Emoji 或插图。

视觉仍以专业、清晰和家长可读为首要目标，不做儿童游戏化界面。

### 14.2 插图使用范围

插图只用于三个场景：

| 场景 | 目的 | 展示方式 |
|---|---|---|
| 综合诊断首页首屏 | 建立亲切感，引导阅读当前结论 | 一张横向主题插图，配一段当前结论 |
| 首次使用或空状态 | 帮助理解产品用途，引导下一步 | 居中插图、简短说明、一个主要行动 |
| 分析中 | 缓解等待焦虑，说明当前进度 | 居中插图、进度信息、查看当前诊断入口 |

插图不得进入：

- 单次报告正文
- 学习卡点列表
- 最近变化和历史记录列表
- 错题详情
- PDF 报告

### 14.3 插图风格

- 简洁友好的扁平插画
- 面向小学生家长，亲切但不幼稚
- 使用数学试卷、放大镜、检查标记、成长等相关视觉线索
- 色彩采用数学学科蓝色，并搭配珊瑚红、暖黄色和绿色
- 不包含文字、字母、数字和复杂背景
- 同一套插图保持角色、线条、色彩和光影一致

首屏插图必须裁切后仍能清楚看到主要人物和“检查试卷”的行为，不使用模糊或纯氛围图片。

### 14.4 图标使用规则

使用统一的线性图标体系。图标优先用于：

- 拍照上传
- 生成验证试卷
- 下载 PDF
- 查看历史
- 当前重点
- 学习卡点
- 最近变化
- 持续出现、需要验证、已有改善

规则：

1. 图标必须和文字标签同时出现，不能只用陌生图标表达核心功能。
2. 同一动作在所有页面使用同一个图标。
3. 状态图标使用不同形状和文字，不能只依赖颜色区分。
4. 主要按钮只保留一个图标，不在按钮内堆叠视觉元素。
5. 图标尺寸、描边和容器尺寸全局统一。

### 14.5 Emoji 使用规则

Emoji 仅作为轻量情绪反馈，不作为正式诊断状态的主要表达。

允许场景：

- 分析完成提示
- 验证通过后的简短正向反馈
- 非关键空状态文案

禁止场景：

- 报告标题和诊断正文
- 卡点状态标签
- 错题详情
- PDF 报告
- 错误和失败提示

### 14.6 色彩与层级

- 数学学科主色继续使用蓝色，用于顶部导航和主要行动。
- 珊瑚红表示持续出现，暖黄色表示需要验证，绿色表示已有改善。
- 状态色只用于标签、图标背景和细小强调，不使用大面积高饱和色块。
- 页面主体继续使用白色与浅灰背景，保证报告内容易读。
- 同一页面只突出一个主要按钮。

### 14.7 动效与反馈

动效只用于帮助用户理解状态变化：

- 卡片点击使用轻微缩放反馈。
- 分析中使用平缓进度动画，不使用持续闪烁。
- 新报告完成后，当前结论与最近变化可以使用一次短暂淡入。
- 验证通过可以使用一次轻量成功反馈。

所有动效应短暂、可忽略，不阻塞操作，不改变布局尺寸。

### 14.8 可读性与适配

- 文字、按钮和状态标签必须在微信字体放大后仍保持完整。
- 图标与文字保持足够对比度和点击热区。
- 插图加载失败时，页面必须仍能通过标题、说明和按钮完整使用。
- 插图资源需要压缩并按实际展示尺寸输出，避免显著增加小程序包体。
