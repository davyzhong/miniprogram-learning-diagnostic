# 扩展 Emoji 兼容性第二批测试设计

## 背景与目标

第一批兼容性测试已在目标 Android 微信真机完成，现有 14 类、202 项全部通过。本期把测试页升级为批次化兼容性实验室，并一次性增加第二批 1000 项候选，以更大范围识别该设备对 Emoji 字符、变体选择符、肤色修饰符、区域旗帜和 ZWJ 组合序列的支持边界。

本期只扩展测试库和测试交互，不自动把通过项投放到正式业务页面。生产白名单仍由 `miniprogram/utils/ui-symbols.js` 独立维护；第二批完成真机测试后，再按产品语义选择需要进入正式界面的图标。

测试结论绑定页面显示的手机型号、Android 版本、微信版本和小程序基础库版本，不推断为所有 Android 或 iOS 设备的通用结论。

## 数据来源与选择方案

- 一般字符和序列以 Unicode Consortium 发布的 [Unicode Emoji 17.0 `emoji-test.txt`](https://www.unicode.org/Public/17.0.0/emoji/emoji-test.txt) 为规范来源，只选择 `fully-qualified` 条目。该文件 SHA-256 固定为 `1d8a944f88d7952f7ef7c5167fef3c67995bcae24543949710231b03a201acda`。
- `B02-C21` 是上述规则的唯一例外：从 [Unicode 17.0 `emoji-variation-sequences.txt`](https://www.unicode.org/Public/17.0.0/ucd/emoji/emoji-variation-sequences.txt) 选择 25 个基字符，每个基字符同时保留 `FE0E` 文本呈现和 `FE0F` Emoji 呈现，共 50 项。该文件 SHA-256 固定为 `bb3d09ef03f206012c7532dd52dc0a21c9efddba0135ea4cf0d9201b8b9bba7e`。
- 中文名称以 [CLDR 48.2 `cldr-common-48.2.zip`](https://unicode.org/Public/cldr/48.2/cldr-common-48.2.zip) 为来源，SHA-256 固定为 `d2844f9dbf6124d11a7b047f5381a467902d82a673be3d658f4c0791ffa0b83b`。提取顺序固定为 `common/annotations/zh.xml` 的 `annotation type="tts"`，再回退到 `common/annotationsDerived/zh.xml` 的 `type="tts"`，最后才使用清单中显式维护的中文回退名。`B02-C21` 在基础短名后固定追加“文本呈现”或“Emoji 呈现”。
- 第一批 202 项按 Unicode 标量序列去重后从第二批排除。不同呈现序列视为不同候选，例如带 `U+FE0F` 和不带 `U+FE0F` 的形式可以分别存在于高风险分类。
- 第二批精确冻结为 1000 项，采用“均衡覆盖”：700 项实用候选和 300 项兼容性高风险候选。
- 同一个 Unicode 标量序列在第二批只能出现一次。选择结果一旦发布，编号、字符序列、所属分类和顺序永久稳定。

第二批不依赖运行时或构建时的主观“优先选择”算法。实施时建立规范清单 `scripts/emoji-compatibility/batch-02-manifest.json`，逐项枚举 `id`、`categoryId`、`order`、Unicode 标量序列、中文名称、名称来源和 Emoji 版本；该 1000 项清单是唯一权威选择结果。生成工具只负责校验上游文件校验和、按规范清单解析字符并生成运行时模块，不自行增删或重新分类。

规范清单按表中固定配额编制；交叉命中的高风险序列以清单显式分类为准，不进行二次推断。清单必须覆盖 `FE0F`、`FE0E`、肤色修饰符、`200D`、区域指示符、tag 字符和 `20E3` 键帽组合，并由快照测试冻结每一项的 `ID -> 序列 -> 分类 -> 顺序 -> 标签` 映射。任何上游校验和错误、分类配额不足、重复序列或最终数量偏差都直接失败，不允许静默少生成。

## 批次与编号规则

### 第一批已通过

- 现有 14 类、202 项归档为“第一批 · 已通过”。
- 现有公开编号 `C01`、`C01-01` 等全部保留，不改写为新格式，避免此前反馈失效。
- 第一批的分类、顺序、Unicode 标量序列和中文名称继续由原冻结清单约束。
- 页面默认折叠第一批，但用户可以进入并逐类复查。

### 第二批待测试

- 批次编号固定为 `B02`。
- 分类编号使用 `B02-C01` 至 `B02-C26`。
- 单项编号使用 `<分类编号>-<三位序号>`，例如 `B02-C03-017`。
- 用户可反馈整批 `B02`、整类 `B02-C03`、单项 `B02-C03-017` 或范围 `B02-C03-017~024`。
- 已发布编号不得删除、复用或改绑其他 Unicode 序列。未来废弃项保留原编号并标记 `deprecated`。

## 页面信息架构

1. 页面顶部继续展示测试环境摘要，并增加总览：`已通过 202`、`待测试 1000`、`共 1202`。
2. 环境摘要下方使用两个批次切换项：
   - `第二批 · 待测试 1000` 默认选中并展开。
   - `第一批 · 已通过 202` 默认折叠；切换后才显示其分类导航和内容。
3. 批次切换不同时展开两套候选网格，避免页面过长和状态混乱。
4. 当前批次内沿用横向分类标签、风险说明、四列候选网格和上一类/下一类导航。
5. 页面状态只保存批次元数据、分类元数据和当前分类项目；WXML 只创建当前分类的 35 或 50 个候选节点。
6. 点击批次编号、分类编号或单项卡片复制对应公开编号。批次标题明确显示“已通过”或“待测试”，不使用颜色作为唯一状态信息。
7. 从第一批切回第二批时，分别恢复两个批次各自最后浏览的分类；首次进入第二批定位 `B02-C01`。
8. 本期不增加逐项勾选、账号同步或云端结果存储。用户仍通过稳定编号集中反馈，以控制实现范围和包体。
9. 首页测试入口的摘要从 `202 项候选 · 14 类` 更新为精确文案 `1202 项候选 · 2 批次`。

## 数据模块边界

- 保留 `emoji-candidates.js` 作为第一批不可变快照，避免破坏既有测试和编号。
- 新增独立的第二批静态数据模块 `miniprogram/pages/icon-compatibility/emoji-candidates-batch-02.js`，包含来源版本、批次元数据、分类元数据和紧凑项目元组。
- 第二批模块对页面暴露标准化分类对象；紧凑存储格式不泄漏到页面控制器。
- 候选数据只存在于 `pages/icon-compatibility` 测试分包。主包首页只保留现有入口和数量摘要，不引入 1000 项数据。
- 生成工具和上游来源校验放在小程序打包目录之外，运行时不联网、不读取远程数据。
- 全局生产 Emoji 扫描的字面量豁免必须精确限定为 `emoji-candidates.js` 和 `emoji-candidates-batch-02.js` 两个候选数据模块。页面控制器、WXML、`ui-symbols.js` 和其他业务页面不豁免；隔离测试禁止生产模块导入第二批数据。
- 风险说明是分类级 `riskNote`。每个项目通过所属分类解析到非空风险说明，项目元组不重复存储该字段；只有确有单项特殊判定时才允许可选覆盖字段。

## 错误处理

- 系统环境 API 失败时继续显示“环境信息不可用”，不阻塞候选测试。
- 无效批次或分类索引统一回退到当前批次第一类。
- 剪贴板 API 缺失、拒绝或抛错时显示“复制失败”，页面状态保持不变。
- 数据模块在测试阶段发现重复 ID、重复序列、数量偏差、空名称、空风险说明或来源版本不符时直接失败，禁止带缺陷清单进入真机测试。

## 性能与包体预算

- 页面始终只渲染当前分类，最大同时渲染 50 个候选卡片，不渲染 1202 个节点。
- 分类切换的 `setData` 只发送当前分类元数据和项目，不发送整个批次。
- 第二批使用紧凑静态结构，避免在每个项目重复批次、分类和状态字符串。
- 第二批数据位于测试分包，编译后主包增量目标不超过 5 KB；测试分包编译后总大小目标不超过 250 KB；整个项目继续低于微信当前配置的包体限制。
- 实施前后沿用 `docs/performance/emoji-compatibility-lab-baseline.md` 的微信开发者工具 Preview/上传配置，记录主包、图标测试分包和总包体的编译前后大小，并确认编译及预览成功。现有图标测试分包基线为 23,906 bytes；若实施后超过 250 KB，优先压缩字段和移除重复元数据，不减少 1000 项测试覆盖。

## 测试与验收

### 数据验收

- 第一批精确为 202 项、14 类，并显示“已通过”。
- 第一批 14 个分类及 202 个项目必须与原冻结规格逐项快照比较，ID、分类顺序、项目顺序、字符、Unicode 标量序列和中文名称均不得变化；“第一批 · 已通过”只作为控制器层批次元数据增加，不修改第一批数据模块。
- 第二批精确为 1000 项、26 类，其中实用分类 700 项、高风险分类 300 项。
- 两批合计 1202 项；第二批内部以及第二批对第一批均无重复 Unicode 标量序列。
- 所有第二批 ID 符合 `B02-Cxx-xxx`，分类 ID、项目 ID 和 `ID -> Unicode 序列` 映射唯一且冻结。
- 所有候选具有非空字符、Unicode 标量序列和中文短名，并能从所属分类解析到非空 `riskNote`。
- 来源版本固定为 Unicode Emoji 17.0 和 CLDR 48.2，生成结果可重复。
- 规范清单逐项冻结 `ID -> 序列 -> 分类 -> 顺序 -> 标签`，并记录名称来源；生成器在相同上游校验和与清单下必须输出字节一致的运行时数据。

### 页面验收

- 首次进入默认显示第二批待测试，不直接展开第一批 202 项。
- 两个批次可切换，状态、数量、分类位置和上一类/下一类边界正确。
- 第一批原编号可复制；第二批批次、分类和单项编号可复制。
- 切换分类时 WXML 只绑定当前分类；两个批次分别保留最后浏览位置。
- 候选显示不存在裁切、编号溢出或分类切换引起的布局跳动。
- 在 320 CSS px 宽的微信开发者工具窄屏视口和目标 Android 真机分别截屏检查最长编号、最长中文名称和最长 ZWJ 序列；连续往返切换至少 10 个分类，网格不得出现空白、旧数据残留或高度跳动。
- 测试页继续是生产 Emoji 扫描的唯一精确豁免边界，其他业务页面不能直接引用第二批候选。
- 首页入口精确显示 `1202 项候选 · 2 批次`，并继续正确进入测试分包。

### 真机验收

- 在目标 Android 微信中逐类检查第二批 26 类。
- `pass`：显示为单个、完整、未裁切且语义正确的预期图形；厂商画风差异不算失败。
- `B02-C21` 使用呈现特定判定：`FE0E` 项只有显示为文本字形才算通过，`FE0F` 项只有显示为 Emoji 图形才算通过；两项应能观察到呈现差异。
- `fail`：显示方框、空白、替代字符、错误语义、严重裁切，或组合序列被拆成多个可见图形。
- `uncertain`：能够显示但无法确认组合完整性或产品可用性，需要截图复核。
- 整类通过可反馈 `B02-C08: pass`；异常必须反馈单项编号或编号范围。最终结果附测试环境和日期。

## 非目标

- 不把第一批或第二批全部自动加入正式业务白名单。
- 不替换当前正式页面的图标设计。
- 不在本期建立多设备兼容性数据库、云端结果同步或管理后台。
- 不承诺 1000 项覆盖 Unicode Emoji 17.0 的全部序列；本期目标是高价值、可反馈、可重复的一次性大规模抽样测试。
